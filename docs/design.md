## 2. いちばん大事な分け方

**engine が計算するのは「部隊」であって「兵」ではない。**

- engine が持つのは、1軍あたり最大16部隊ぶんの、位置・向き・兵数・士気・状態だけ。
- 部隊の中に並ぶ小さな兵は、client が兵数から描き起こす飾りで、engine は関知しない。
- 戦闘を映す側（client）は、engine の状態を直接読まず、`BattleSource`（§5.2）から届く「場面」だけを描く。1人用と対戦で同じ描画が使え、あとから斜め視点も足せる。

## 3. engine

### 3.1 原則

- **再現できる**。同じ初期状態・同じ種・同じ入力からは、同じ結果が出る。`Math.random`・`Date.now`・時計・通信に触れない。乱数は状態の中に持つ（32ビットの種から進める）。
- **時間は刻みで進む**。1刻み = 0.1秒（`DT = 0.1`）。engine は実時間を知らない。呼ぶ側が `step` を呼んだ回数だけ進む。毎秒いくつ、と書いた数字は、刻みごとに `DT` をかけて使う。
- **状態は JSON にそのまま保存できる形**。`Map`・`Set`・クラスのインスタンス・`undefined` の値を持たない。
- **例外を投げない**。不正な入力はエラーの結果として返す。利用者の入力が届く口（`createBattle`、`validateArmy`、`canOrder`、`canOrderView`、`applyTemplate`、`step` に渡す号令）は、どんな値を渡されても例外を投げない。`step` に渡す号令のうち不正なものは、無視して状態を変えない。
- **`step` に渡す状態は調べない**。状態は「`createBattle` が作り、`step` だけが書き換え、JSON にして戻しただけのもの」を前提にする。サーバーは、利用者から状態を受け取らない。
- **入力の量に上限を置く**。配置の数は、中身を見る前に上限で調べる。1回の `step` で見る号令は先頭の8件まで。予定された号令は32件まで。
- `step` は渡された状態を書き換える（毎刻みの複製を避けるため）。複製が要る側は自分で複製する。
- **判断は、刻みの初めの状態だけを見て行う**。どの部隊も、その刻みの初めの全部隊の位置・向き・状態を見て、狙い・動き・攻撃を決める。動きもダメージも士気も、全部隊ぶんを計算してから同時に適用する。処理する順番（id の順）で結果が変わらないようにする。
- 同点のときは、id の小さいほうを選ぶ。

**刻みの数え方**

- `state.tick` は、終わった `step` の回数。開戦時は 0。
- `step` は「刻み t = `state.tick`」を処理し、最後に `state.tick` を 1 増やす。
- 号令の期限は `untilTick` で持ち、`state.tick < untilTick` の間だけ有効。刻み t にかかった10秒の号令は `untilTick = t + 100` で、ちょうど100刻みのあいだ効く。
- 予定された号令（`scriptedOrders`）の `tick = t` は、`state.tick === t` の `step` の初めに出る。`tick = 0` は最初の `step` で出る。
- `step` の終わりに `state.tick === maxTicks` になり、決着していなければ時間切れ。標準の 1800 なら、ちょうど 1800 回の `step` で終わる（その前に膠着（§3.6.4）で終わらなければ）。

**初期状態**

- id は、陣営0の配置を配列の順に 0 から、続けて陣営1の配置を配列の順に振る。
- 士気は 100。向きは自陣営の「前」。兵数は兵種の最大値。小数のまま持つ（映す側が切り上げて表示する）。
- 状態は `active`。狙いはなし。号令はなし。

### 3.2 座標と戦場

- 単位はマス。戦場は横 `width` × 縦 `height`。標準は 12 × 16（自軍の配置エリア6 + 中間地帯4 + 敵軍の配置エリア6）。
- 陣営は `0` と `1`。陣営0の配置エリアは下側（y が 10〜16）、陣営1は上側（y が 0〜6）。陣営0の「前」は y が減る向き、陣営1は増える向き。
- 部隊の位置はマスの中心（列 + 0.5、行 + 0.5）から始まり、戦闘中は連続した値で動く。
- 部隊の中心は、戦場の端から 0.45 より内側に保つ（敗走中を除く）。
- 地形はマスごとに持つ（§3.8）。段階1〜3はすべて平地だが、型と受け渡しは最初から入れておく。
- 翼は、配置した列で決まる：自分から見て左の3分の1が左翼、右の3分の1が右翼、あいだが中央。陣営1は向きが逆なので、列の大きいほうが左翼になる。戦闘中に動いても、翼は変わらない。

### 3.3 型

```ts
type Side = 0 | 1;
type Kind = 'infantry' | 'shield' | 'cavalry' | 'archer' | 'hq';
type UnitKind = Kind | 'gate';   // 門（段階4、§3.8）。配置には使えず、BattleSetup.gate で置く。映す側には BattleView.gate で別に渡す
type Stance = 'advance' | 'hold' | 'flank' | 'hunt';               // 前進・守備・迂回・本陣狙い
type OrderKind = 'charge' | 'brace' | 'retreat';                   // 突撃・堅守・後退
type OrderTarget = 'all' | 'left' | 'center' | 'right';
type Terrain = 'plain' | 'hill' | 'forest' | 'river' | 'fence' | 'wall';

interface Placement { kind: Kind; col: number; row: number; stance: Stance }

interface Field {
  width: number; height: number;
  terrain: Terrain[];                       // 行優先。長さは width × height
  zones: [Zone, Zone];                      // 陣営ごとの配置エリア（マスの矩形）
}

interface BattleSetup {
  field: Field;
  armies: [Placement[], Placement[]];       // 戦場の座標で書く
  seed: number;
  maxTicks: number;                         // 標準は 1800（3分）
  timeout: 'compare' | 'side0_wins' | 'side0_loses';
  scriptedOrders?: { tick: number; side: Side; target: OrderTarget; kind: OrderKind }[];  // ステージの敵の号令
  requireHq?: boolean;                      // 既定は true。false は部分的な戦いのテスト用（下記）
  stalemate?: boolean;                      // 既定は true。false は膠着の決まり（§3.6.4）を切る。部品のテスト用
}

interface Unit {
  id: number; side: Side; kind: Kind; wing: 'left' | 'center' | 'right';
  x: number; y: number; fx: number; fy: number;     // 位置と、向きの単位ベクトル
  men: number; maxMen: number; morale: number;      // 士気は 0〜100
  stance: Stance; home: { x: number; y: number };
  status: 'active' | 'routing' | 'gone';
  goneReason: null | 'routed' | 'destroyed';
  target: number | null;                            // 攻撃し、向く相手（§3.6.1）
  order: null | { kind: OrderKind; untilTick: number };
  stats: { dealt: number; taken: number; flankDealt: number; routsCaused: number };
  // ほかに、迂回の進み具合・騎兵の助走距離・最後に撃たれた刻み・敗走を始めた刻みを持つ
}

interface BattleState {
  tick: number; rng: number; field: Field; units: Unit[];
  ordersUsed: [number, number];
  maxTicks: number; timeout: BattleSetup['timeout'];
  outcome: null | { winner: Side | 'draw'; reason: 'hq' | 'wipeout' | 'timeout' | 'stalemate' | 'gate'; tick: number };
  quietTicks: number | null;                // 膠着の時計（§3.6.4）。静かな刻みが続いた数。null は決まりを切った戦い
  // ほかに、開戦時の兵数の合計、最初に消えた部隊の記録、予定された号令、
  // 前の刻みに敗走・全滅した部隊の一覧（次の刻みの士気の計算に使う）
}
```

- `requireHq: false` のとき、本陣のない軍を認める。本陣のない軍には「本陣を討たれた」の負けはなく、全部隊が消えたら負け。合格条件の小さな場面（§3.9）のためのもので、画面からは使わない。
- 状態はただの JSON なので、テストは `createBattle` のあとで部隊の値を書き換えて場面を作ってよい。

### 3.4 公開する関数

```ts
createBattle(setup: BattleSetup): Result<BattleState>      // 配置を検査してから作る
step(state: BattleState, orders: OrderInput[]): BattleEvent[]   // 1刻み進める。決着後は何もしない
canOrder(state, side, target, kind): Result<true>          // §3.6.5 の受付の条件
viewFor(state: BattleState, viewer: Side | 'both'): BattleView  // 映す側に渡す場面
summarize(state: BattleState): BattleSummary               // 振り返り用

validateArmy(placements, zone, limits): ArmyError[]        // マスの重なり・エリア外・本陣の数・予算・部隊数
armyCost(placements): number
defaultStance(kind): Stance
wingOf(col, field, side): 'left' | 'center' | 'right'

listTemplates(): TemplateInfo[]                            // ひな形（§3.7）
applyTemplate(id, roster, zone, side): Placement[]
recognizeFormation(placements, zone, side): { id: string; name: string } | null   // 段階2

STAGES: Stage[]                                            // ステージのデータ（§3.10）。段階2
PVP_RULES: { budget, costs, maxUnits }                     // 対戦の予算。段階3
```

**映す側に渡す型は、渡してよい項目だけを書き出して作る**（状態をそのまま複製して項目を消す作りにしない）。

```ts
interface UnitView {
  id: number; side: Side; kind: Kind; wing: 'left' | 'center' | 'right';
  x: number; y: number; fx: number; fy: number;
  men: number; maxMen: number; morale: number;
  status: 'active' | 'routing' | 'gone';
  order: OrderKind | null;
  attacking: number | null;        // この刻みに実際に攻撃した相手（近接でも弓でも）。攻撃していなければ null
  stance?: Stance;                 // 自軍の部隊だけ。viewer が 'both' なら全部隊
}
interface BattleView {
  tick: number; maxTicks: number; units: UnitView[];
  ordersLeft: [number, number];
  outcome: BattleState['outcome'];
}
type BattleEvent =
  | { type: 'order'; tick: number; side: Side; target: OrderTarget; kind: OrderKind }
  | { type: 'rout'; tick: number; unit: number }
  | { type: 'destroyed'; tick: number; unit: number }
  | { type: 'impact'; tick: number; attacker: number; defender: number; facing: 'front' | 'side' | 'rear' }  // 騎兵の突入
  | { type: 'end'; tick: number; winner: Side | 'draw'; reason: string };
interface BattleSummary {
  winner: Side | 'draw'; reason: string; seconds: number;
  remaining: [number, number];          // 残った兵の割合。敗走・全滅した部隊は0と数える
  units: { id: number; side: Side; kind: Kind; menLeft: number; dealt: number; routsCaused: number; fate: 'alive' | 'routed' | 'destroyed' }[];
  firstBroken: [number | null, number | null];   // 陣営ごとに、最初に消えた部隊
}
```

- `attacking` は、戦場を見ていれば分かること（誰が誰を打っているか、誰に矢が飛んでいるか）なので、両軍ぶんを渡す。向かっているだけで、まだ攻撃していない相手（狙い）は渡さない。
- 相手の部隊の方針・狙い・持ち場・迂回の進み具合・助走は、`BattleView` に含めない。出来事にも含めない。テストで、相手ぶんの `UnitView` に上の項目以外の鍵がないことを確かめる。
- 出来事は、1部隊につき敗走1回・全滅1回まで。

### 3.5 部隊の数字（初期値）

| 兵種 | 兵数 | 速さ（マス/秒） | 近接の攻撃（毎秒） | 回転（度/秒） | 特徴 |
|---|---|---|---|---|---|
| 歩兵 | 100 | 1.0 | 3.0 | 180 | なし |
| 盾兵 | 100 | 0.7 | 2.2 | 120 | 正面からの近接は 0.45 倍、弓は 0.4 倍。正面からの騎兵の突入を止める |
| 騎兵 | 60 | 2.2 | 3.6 | 240 | 助走をつけて当たると突入（§3.6.2） |
| 弓兵 | 80 | 0.9 | 1.2 | 180 | 4.5 マス先まで撃てる（毎秒 2.4）。近接で受ける損害は 1.3 倍 |
| 本陣 | 80 | 0.6 | 2.6 | 120 | 受ける損害は 0.7 倍。3.5 マス以内の味方の士気を支える |

- 部隊どうしの中心は、味方でも敵でも 0.9 より近づかない（§3.6④）。
- 近接が届く距離（近接の距離）は、中心どうしで 1.05。

### 3.6 1刻みの中身

順番は次のとおり。①〜③と⑤〜⑦の判断は、刻みの初めの状態を見て行う。

1. **号令を受け付ける**（§3.6.5）。予定された号令も、ここで出す。
2. **切れた号令を外す**（`state.tick >= untilTick`）。外すときの後始末は §3.6.5。
3. **狙いと、動く向きを決める**（§3.6.1）。
4. **動く**（下記）。
5. **向きを変える**。向きたい方向へ、回転の上限つきで回る。向きたい方向は、狙いがあれば狙いのほう、なければ動く向き、どちらもなければ自陣営の「前」。後退の号令中は、狙いにかかわらず動く向き（後ろ）。
6. **戦う**（§3.6.2）。
7. **兵数と士気をまとめて動かす**（§3.6.3）。兵数が0以下の部隊は全滅（`gone`）、士気が0以下の部隊は敗走（`routing`）にする。両方なら全滅。
8. **決着を調べる**（§3.6.4）。
9. `state.tick` を 1 増やす。時間切れと膠着を調べる（§3.6.4）。

**状態ごとの扱い**

| | `active` | `routing` | `gone` |
|---|---|---|---|
| 動く | 方針と号令に従う | 自陣の奥へまっすぐ、速さ 1.3 倍で逃げる。敗走した次の刻みから | 動かない |
| 攻撃する | する | しない | しない |
| 攻撃される | される | いま狙われている相手からだけ、される（下記） | されない |
| ほかの部隊とぶつかる | ぶつかる | ぶつからない（すり抜ける） | ぶつからない |
| 味方の支え・本陣の支え・囲みに数える | 数える | 数えない | 数えない |
| 号令がかかる | かかる | かからない | かからない |

- 敗走中の部隊は、戦場の端を越えるか、敗走から5秒（50刻み）たつと `gone`（理由は `routed`）になる。立て直しはしない。
- 敗走中の部隊が追い打ちで全滅しても、まわりの士気への影響は、敗走したときの1回だけ（全滅のぶんは足さない）。
- 敗走した部隊を狙っていた部隊は、その部隊が近接の距離（弓兵なら撃てる距離）にいる間だけ、攻撃を続けてよい。新しく狙う相手に、敗走中の部隊は選ばない。

**④ 動き方**

1. 各部隊が、刻みの初めの位置から、動きたい分（向き × 速さ × `DT`）を決める。戦う部隊と、守備・堅守で持ち場にいる部隊は、動かない。この「動かない部隊」を、この刻みの**錨**と呼ぶ。
2. 動きたい先が、ほかの `active` な部隊（味方でも敵でも。刻みの初めの位置で見る）の 0.9 以内に入るなら、0.9 の手前で止まり、残りの分は、相手のまわりを回る向き（接線）に半分の速さで進む。回る向きは、動きたい向きに近いほう。真正面なら、狙いが左右どちらにあるかで決め、それも同じなら左。
3. 全部隊を同時に動かす。
4. 重なりをほどく。2回くり返す：中心が 0.9 より近い `active` な2部隊を、結ぶ線に沿って、重なりの半分ずつ離す。片方が錨なら、もう片方だけを重なりの分ぜんぶ動かす。両方が錨なら動かさない。位置がまったく同じなら、id の小さいほうを左、大きいほうを右へ離す。くり返しの中の計算は、その回の初めの位置で行い、同時に適用する。
5. 戦場の内側（端から 0.45）に収める。

- 守備の味方が横に並んでいて、そのすき間にはまったときは、§3.6.6 の決まりで並びの端へ回り込む。
- この決まりで、戦っている味方の後ろの部隊は、通り抜けずに脇へ回り込む。列の端からあふれた部隊が敵の側面に回り、敵の列に穴が空けば後ろの部隊がそこへ入る。包囲と突破は、ここから生まれる。

#### 3.6.1 狙いと方針

部隊は、狙い（`target`）を1つだけ持つ。**狙いは、攻撃する相手であり、向く相手でもある。**

**近接の距離に敵がいるとき**（どの方針でも同じ。ただし下の「戦わない場合」を除く）

- いまの狙いが近接の距離にいれば、狙いを変えない。後ろや横から別の敵が当たっても、向きは変わらない。これが、側面・背面を突かれる仕組みになる。
- いまの狙いが近接の距離にいなければ、近接の距離にいる敵のうち、いまの向きにいちばん近い方向にいる敵を狙う。同じなら近いほう。
- この部隊は戦う（動かない）。

**近接の距離に敵がいないとき**

| 方針 | 狙いと動き |
|---|---|
| 前進 | `距離 + 横のずれ（x の差の絶対値）` がいちばん小さい敵を狙い、そちらへ進む。いまの狙いが残っている間は、ほかの敵の値が 1.0 以上小さくならない限り、狙いを変えない |
| 守備 | 持ち場（`home`）にいる。持ち場から 0.1 より離れていたら戻る。4マス以内に敵がいれば、いちばん近い敵を狙う（向くだけで、近づかない） |
| 迂回 | ①自分に近いほうの端の列（端から 0.5）へ横に出る。②端に沿って、開戦時の敵軍の重心の行より 1.5 マス奥（敵陣側）まで進む。戦場に収まらなければ収まるところまで。③そこから、本陣以外でいちばん近い敵を狙って進む（本陣しか残っていなければ本陣）。①②の間は狙いを持たない。途中で敵と戦って、その敵が消えたら、続きから再開する |
| 本陣狙い | 敵の本陣を狙い、まっすぐそちらへ進む。途中の敵にぶつかったら、④の決まりで相手のまわりを回り、敵の列に沿って滑って、端か穴から抜ける。敵の本陣がなければ、前進と同じ |

- 迂回で、左右どちらの端も同じ近さのときは、開戦時にその側にいる敵の部隊が少ないほうへ出る。それも同じなら左。
- 本陣狙いの部隊は、**本陣以外の敵とは戦わない**（正面にいても戦わず、すれ違う敵から打たれながら進む）。戦うのは、敵の本陣が近接の距離に入ったときだけ。
  - 滑る向き（左右）は、何かにぶつかり続けている間は変えない。何にもぶつからずに動けた刻みで、決め直す。ただし、保った向きに滑ると後ろ（本陣から遠ざかる向き）へ進むことになったら、保つのをやめて決め直す（味方どうしが詰まって、互いのまわりを回りながら下がり続けるのを防ぐ）。
  - 詰まったとき：2秒前の位置から 0.3 マスも進めていなければ、近接の距離にいるいちばん近い敵と戦う。その敵が消えるか離れたら、また本陣へ向かう。
- 迂回の①②の部隊は、近接の距離に敵がいても、その敵が進む向きの正面（±50°以内）にいなければ戦わずに進み続ける。正面にいれば、ふつうに戦う。
- 狙いが消えたら（敗走して攻撃を続けられなくなった場合を含む）、その刻みから上の決まりで選び直す。

**兵種ごとの違い**

- 弓兵は、近接の距離に敵がいなければ撃つ。撃てる距離（4.5）にいる `active` な敵のうち、いちばん近い敵を狙う。前進・迂回の③・本陣狙いの弓兵は、撃てる相手がいる間は止まって撃つ。守備の弓兵は持ち場から撃つ。味方には当たらず、味方ごしに撃てる。
- 弓兵は、近接の距離（1.05）に敵がいる間は撃てず、近接で戦う。
- 本陣が選べる方針は、守備と前進だけ。
- 初期設定：歩兵は前進、盾兵は守備、騎兵は迂回、弓兵は前進、本陣は守備。

**優先する順番**：敗走 → 号令 → 兵種ごとの違い → 方針。号令中の動きは §3.6.5。

#### 3.6.2 損害

損害は、次の3つの掛け算で出す。部隊は、狙いにだけ攻撃する（1刻みに1相手）。

```
損害 = もとの値 × 攻める側の倍率 × 受ける側の倍率
```

| | 近接（毎秒） | 弓（毎秒） | 騎兵の突入（1回） |
|---|---|---|---|
| もとの値 | 兵種の攻撃 | 2.4 | 12 |
| × √(攻める側の兵数 ÷ 最大兵数) | かける | かける | かける |
| × ばらつき（0.9〜1.1 の乱数） | かける | かける | かけない |
| 攻める側：突撃の号令中 1.3 | かける | かける | かける |
| 攻める側：相性 | 騎兵→弓兵 1.5、歩兵→弓兵 1.2 | なし | なし |
| 受ける側：向き | 正面 1.0、側面 1.5、背面 2.0 | かけない | 正面 1.0、側面 1.5、背面 2.0 |
| 受ける側：盾兵の正面 | 向きの代わりに 0.45 | 0.4 | 向きの代わりに 0.2 |
| 受ける側：本陣 0.7、弓兵（近接と突入）1.3 | かける | 本陣だけ | かける |
| 受ける側：突撃中 1.2、堅守中 0.7 | かける | かける | かける |
| 地形（§3.8） | かける | かける | かける |

- **向き**は、受ける側の向きと、受ける側から攻める側への方向のなす角で決める：50°以内が正面、120°を超えると背面、あいだが側面。
- 正面の角度は 52° より小さくしておく。正面の相手と組み合っている部隊に、3部隊目が近接の距離まで寄ると、部隊どうしの間隔（0.9）のせいで、角度は必ず 52° ほどより外になる。これを側面と数えないと、列の端から回り込んでも側面にならず、包囲が生まれない。
- **騎兵の突入**：騎兵が、近接の距離に敵がいない状態で続けて 2.0 マス以上動いたあと（止まった刻みで、助走は 0 に戻る）、狙いが近接の距離に入った刻みに、1回だけ起きる。上の損害に加えて、士気への衝撃（正面 −10、側面 −18、背面 −25。堅守中は 0.6 倍）を与える。盾兵の正面に当たった場合は、士気への衝撃はなく、騎兵のほうが兵数 8 と士気 8 を失う。森の中の相手・柵の中の相手には起きない。起きたら助走は 0 に戻る。
- 損害は、残っている兵数までしか入らない。`stats.dealt` と `stats.taken` には、実際に入った分を足す。側面・背面から与えた近接と突入の損害は `stats.flankDealt` にも足す。

#### 3.6.3 士気

1刻みの士気の増減を、部隊ごとにすべて足し合わせてから、1回で適用する。そのあと 0〜100 に収めて、敗走を判定する。

**損害による減り**（損害1件ごとに計算して足す）

```
士気の減り = (その損害で失った兵数 ÷ 最大兵数) × 120 × 向き × 支え
```

- 向き：近接と突入は、正面 1.0、側面 1.6、背面 2.4。弓は向きにかかわらず 0.6。
- 支え：1.6 マス以内の `active` な味方（自分を除く。本陣も1部隊として数える）1部隊ごとに 0.15 軽くなる（3部隊まで。つまり最小 0.55）。本陣が 3.5 マス以内なら、さらに 0.7 倍（本陣自身にはかからない）。堅守中は、さらに 0.6 倍。

**そのほかの増減**

| 条件 | 増減 |
|---|---|
| 囲まれている：近接で攻めてくる敵が2部隊以上いて、そのうち2部隊の方向が 100°以上開いている | 毎秒 −2 |
| 騎兵の突入を受けた | §3.6.2 の衝撃 |
| 前の刻みに、2.0 マス以内の味方が敗走した | 1部隊につき −12 |
| 前の刻みに、2.0 マス以内の味方が全滅した | 1部隊につき −6 |
| 前の刻みに、自分が狙っていた敵が敗走・全滅した | +8 |
| 前の刻みに、2.5 マス以内の敵が敗走・全滅した（上を除く） | 1部隊につき +3 |
| 2.0 マス以内に敵がおらず、この2秒のあいだ損害を受けていない | 毎秒 +1.5 |
| 本陣が 3.5 マス以内にいる（本陣自身を除く） | 毎秒 +1 |
| 号令がかかった刻み | 突撃 +5、堅守 +10 |

- **敗走・全滅の影響は、次の刻みに伝わる**。刻み t に敗走した部隊のまわりの味方は、刻み t+1 の計算で −12 を受ける。それで崩れた部隊の影響は、刻み t+2 に伝わる。崩れは、0.1 秒に1部隊ぶんずつ、波のように広がる。
- 「自分が狙っていた」は、その敵が消えた刻みの初めに、その敵を狙いにしていた部隊すべて。`stats.routsCaused` も、その全部隊に 1 ずつ足す。

#### 3.6.4 決着

刻みの終わりに、陣営ごとに「負けの条件」を調べる。

- **本陣**：本陣が全滅・敗走した（`routing` になった刻みで成立。消えるのを待たない）。
- **壊滅**：本陣以外の部隊が、すべて全滅・敗走した（最後の1部隊が `routing` か `gone` になった刻みで成立）。

| 条件を満たした陣営 | 結果 |
|---|---|
| 片方だけ | もう片方の勝ち。理由は、本陣の条件を満たしていれば `hq`、そうでなければ `wipeout` |
| 両方 | 引き分け。理由は、どちらかが本陣の条件を満たしていれば `hq`、そうでなければ `wipeout` |
| どちらもなし | 続行。`state.tick` を増やしたあと `maxTicks` に達していれば時間切れ（`timeout`）。達していなくて、膠着の時計が満ちていれば膠着（`stalemate`） |

- 同じ刻みに、決着と時間切れが重なったら、決着を優先する。
- 時間切れの `compare`：残った兵の割合（`active` な部隊の兵数の合計 ÷ 開戦時の兵数の合計。本陣を含む）を、百分率に四捨五入して比べる。大きいほうの勝ち。同じなら引き分け。
- `side0_wins`・`side0_loses` はステージ用。

**膠着（2026-11-17 に追加）**

守備どうしが向き合ったまま、だれも攻めない戦いは、時間切れまで何も起きない（鶴翼どうしは 100戦すべて、3-2 に鶴翼・方円をそのまま置くと 40戦すべてが、こうなっていた）。待つだけの時間をなくすために、何も起きないまま 10 秒たったら、そこで終える。ユーザーが決めた（`decisions.md` の「勝敗と1戦の長さ」）。

- **静かな刻み**：次のすべてを満たす刻み。
  1. その刻みに、だれも攻撃していない（⑥のあと、`attacking` がすべて `null`）。門への攻撃も攻撃に数える。
  2. その刻みに、だれも動こうとしていない：戦場にいる部隊（`active` と `routing`。門は除く）の、③で決めた動く向き（回り込みを決めたあとの `dx`・`dy`）が、すべて 0。**実際に動いた距離ではなく、動こうとしたかで見る**。味方に引っかかって少しずつしか進めない部隊は、動こうとしているので静かではない（下の「位置で見ない理由」）。敗走中の部隊はいつも逃げようとするので、いるあいだは静かではない。
  3. 効いている号令がない（その刻みの終わりに、`active` な部隊の `order` がすべて `null`）。
  4. 予定された号令が残っていない（`scriptedNext` が最後まで進んでいる）。
- **時計**：`state.quietTicks`。静かな刻みなら 1 増やし、そうでなければ 0 に戻す。開戦のときは 0。
- **膠着**：決着も時間切れも付いていなくて、`quietTicks >= stalemateTicks`（100）なら、そこで終える。勝ち負けは時間切れと同じ決め方（`compare`／`side0_wins`／`side0_loses`）。理由は `stalemate`、`outcome.tick` はその刻み。
- 優先の順は、決着（門・本陣・壊滅）、時間切れ、膠着。同じ刻みに重なったら、前のものを採る。
- 号令を出せる回数が残っていても、時計は止めない。人が「15秒待ってから突撃」のように遊ぶと、その前に終わることがある。**予定された号令**（面の敵の号令と、見本の号令）は、残っているあいだ時計を止める。面の敵が決まった時刻に動くのを、待たずに終えないため。
- `BattleSetup.stalemate` が `false` の戦いは、`state.quietTicks` が `null` で、膠着で終わらない。動かない部隊を長く見るテスト（時間切れの判定、動けない配置を 60 秒見る D4 など）のためのもの。**テストの共通の入口（`test/helpers.ts` の `battle()`）では切らない**。長く見ることが目的のテストだけ、個別に `false` を渡す（共通で切ると、多くのテストが本番と違う決まりで通ってしまう）。面、対戦、総当たり、T10 は、既定（`true`）のまま流す。
- 保存してあった戦い（`quietTicks` の項目がない状態）を `step` に渡したら、0 から数える（§3.6.6 の `advMoves` と同じ扱い）。`null`（切った戦い）は `null` のままにし、数え始めない。
- `view` には、時計を載せない（画面で使わないため）。
- 結果の理由に `stalemate` が増える。古い版の画面（読み込み済みのまま遊んでいる人）は、知らない理由を空の文字にするので、理由の欄が空になるだけで、壊れない。

**位置で見ない理由**：最初は「時計を始めた位置から 0.3 以内にいれば、動いていない」と決めた。Codex のレビューで、これでは勝ち負けが変わる配置が見つかった。陣営0が 歩兵（列1・行14、迂回）、弓兵（列0・行12、守備）、弓兵（列2・行12、迂回）、本陣（列11・行15）、陣営1が 歩兵（列5・行1、守備）、本陣（列11・行0）、平原、種1。迂回の2部隊は、守備の弓兵に引っかかって、40 秒かけて 0.3 以内を少しずつ進み、そのあと抜け出して 77 秒に攻撃を始め、92 秒に陣営0が勝つ。位置で見ると、12 秒で引き分けにしてしまう。この2部隊は毎刻み動こうとしているので、「動こうとしたか」で見れば、静かな刻みは1つもない（K9）。

**入れる前に測ったこと**（決まりを入れる前の engine に、③の「動こうとしている部隊の数」を外から読める印だけを足して、上の定義の時計を回した。`balance.md` §5.8）：総当たり 49組（鏡写しを含む）× 種10、対戦用の戦場3つ × 49組 × 種4、15面 ×（見本 + ひな形7つ）× 種20、1-2 の標本 400戦、A8・A11・A14 の場面、T10 の 20戦の、合わせて約 4,500戦。

- 10 秒で終えても、**いま決着（本陣・壊滅・門）で終わっている戦いは、1戦も変わらない**。時計が満ちたあとに攻撃が起きる戦いもない（5 秒から 30 秒のどれで切っても同じ）。
- 決まりが働くのは、いま時間切れの戦いのうち、鶴翼どうし、鶴翼 対 方円、方円どうし（開戦から 10 秒）、全部隊が守備どうし（10 秒）、3-2 に鶴翼・方円をそのまま置いたとき。終わるのは平均 30〜47 秒。
- **働かない時間切れ**：鶴翼 対 鋒矢、横陣 対 鶴翼、A11 の守りと攻め、1-5 に偃月をそのまま置いたとき。どれも、弓兵が最後まで撃ち続けて兵が減り続けている（膠着ではなく、遅い戦い）。これは時間切れのまま。
- T10 の 20戦は、決まりが働かない。記録は作り直さない。
- 位置で見る定義（0.3 以内）でも、動こうとしたかで見る定義でも、この約 4,500戦では、働く戦いの数は同じだった（違いが出るのは、上の Codex の配置のような、引っかかって少しずつ進む形）。

#### 3.6.5 号令

**受け付けの条件**（1つでも外れたら受け付けず、回数も減らず、状態も変わらない）

- 決着していない。
- その陣営の使った回数が 3 未満。
- 対象の翼（`all` なら全軍）に、その号令がかかる `active` な部隊が1つ以上いる。突撃は本陣にかからないので、本陣しかいない翼への突撃は受け付けない。

同じ `step` に複数の号令が来たら、配列の順に1つずつ調べる。

| 号令 | 続く長さ | 号令中の動き |
|---|---|---|
| 突撃 | 10秒 | 方針が前進になる（弓兵は、撃てる相手がいれば止まって撃つ）。攻撃 1.3 倍、受ける損害 1.2 倍、速さ 1.25 倍。本陣にはかからない |
| 堅守 | 10秒 | その場で止まる（持ち場には戻らない）。近接の距離の敵とは戦い、弓兵は撃つ。受ける損害 0.7 倍、士気の減り 0.6 倍 |
| 後退 | 6秒 | 自陣の奥へまっすぐ下がる。**戦わず、撃たない**。近接の距離に敵がいても動く。向きは、回転の上限つきで後ろへ回る（背中を見せる）。配置エリアのいちばん奥の2行に入ったら止まり、そこからは堅守と同じ動き（倍率はなし）で残りの時間を過ごす |

- 号令がかかった部隊は、それまでの号令が終わり、新しい号令に入れ替わる。同じ種類の号令をもう一度かけてもよい（長さが延び、士気の上乗せももう一度入る。回数は減る）。
- **号令が終わるときの後始末**（期限が来たとき、新しい号令に入れ替わるとき、どちらでも）：方針が守備の部隊は、その時点の位置を新しい持ち場にする。迂回の部隊は、進み具合をそのまま引き継ぐ。
- 号令が終わったら、元の方針に戻る。

#### 3.6.6 守備の味方の並びを回り込む（2026-11-17 に追加）

**なぜ足すか**

- 守備の味方が横に並んでいると、そのすぐ後ろの前進の部隊は、味方と味方のすき間（幅 1.0。通るには 1.8 要る）にはまり、左右に小刻みに動くだけで、いつまでも前へ出られなかった。④-2 の「相手のまわりを回る」は、相手が1部隊のときしか抜けられない。
- 公開先での試遊（1-2 で盾兵3の後ろに歩兵2を置いた）で見つかった。画面なしで測ると、この配置は種20個すべてで歩兵2部隊が 176 秒止まり続けた。総当たり 420 戦では 80 戦で起き、すべて鶴翼（中央の盾兵の後ろに弓兵がいる）が入った戦いだった。15面の見本では起きていない。
- 戦っている味方（守備でない）の後ろで待つのは、これまでどおりとする。前の味方が倒れれば穴に入れるので、待つ意味がある。**直すのは、放っておくと最後まで動かない味方にふさがれた場合だけ**。

**言葉**

- **持ち場の守り手**：`active` で、方針が守備（本陣を含む）で、号令がかかっておらず、持ち場から `homeTolerance`（0.1）以内にいる部隊。戦っていても、守り手である。号令が終わって持ち場が置き直された部隊（§3.6.5）も、その新しい持ち場にいれば守り手である。門は守り手に数えない。
- **前へ進む動き**：その刻みの動きが、前進の決まり（`planAdvance`。方針が前進、突撃の号令中、迂回の③、敵の本陣がないときの本陣狙い）で決まり、狙いがあり、その刻みに戦っても撃ってもいない（錨でない）こと。迂回の①②と、敵の本陣へ向かう本陣狙いには、この決まりをかけない。

**決まり**

1. **動いた分を覚える**：ふつうの「前へ進む動き」をした刻み（回り込み中でない刻み）ごとに、実際に動いた分（重なりをほどき、戦場と城壁に収めたあとの位置から、刻みの初めの位置を引いたもの）を `advMoves` に足す。最大 `detourStuckTicks`（50 刻み = 5 秒）個で、古いものから捨てる。それ以外の刻み（戦った・撃った・号令で止まった・狙いがない・回り込み中）には、空にする。本陣狙いの `huntMoves` と同じ形にする。
2. **ふさがれたと判定する**（刻みの初めの位置で）：`advMoves` が 50 個たまっていて、その合計（ベクトルの和）の長さが `detourStuckDist`（0.3）未満で、かつ、**ふさいでいる守り手**がいる。ふさいでいる守り手とは、同じ陣営の持ち場の守り手のうち、中心が自分から `spacing + detourReach`（0.9 + 0.1）以内にあり、動きたい向きの側にいる（自分から守り手への向きと、動きたい向きの内積が正）もの。
3. **出口を選ぶ**：ふさいでいる守り手すべてから、「同じ陣営の持ち場の守り手で、中心どうしが `spacing × 2`（1.8）未満」をたどってつながる集まりを**並び**と呼ぶ。並びの x のいちばん小さい値を `xL`、大きい値を `xR` として、出口を2つ考える：`xL − (spacing + detourGap)` と `xR + (spacing + detourGap)`（`detourGap` は 0.05）。
   - 出口は、次の2つをどちらも満たせば**開いている**：(a) 出口の x が `edgeMargin` 以上、`幅 − edgeMargin` 以下。(b) 真横の道がふさがっていない。つまり、並びの部隊のうち、中心の y が自分の y から 0.5 未満で、x が自分の x と出口の x の間（両端を含まない）にあるものがいない。(b) は、方円の内側のように、横にも守り手がいて出られない形を外すための条件。
   - 開いている出口のうち、`|出口 − 自分の x| + |狙いの x − 出口|` が小さいほうを選ぶ。差が 1e-9 以内なら、自軍から見て左（陣営0は x の小さいほう、陣営1は大きいほう）。部隊の id や、戦場の座標の左右そのものは、決め手に使わない（陣営を入れ替えて 180° 回した戦いが、同じ結果になるようにする）。
   - 開いている出口がなければ、回り込まない。`advMoves` を空にする（5 秒後に、もう一度判定する）。
4. **回り込む**：選んだ出口の x を `detourX` に覚え、`detourTicks` を 0 にする。回り込み中は、動きたい分を「真横に、`detourX` へ」に置き換える。速さは、その刻みのふつうの決まりで出た速さ（突撃の号令中なら、その倍率も入る）。残りが1刻みぶんより短ければ、残りだけ動く（`detourX` ちょうどに着く）。ぶつかったときは④のふつうの決まり（本陣狙いの「回る側を保つ」は使わない）。狙いと向きは、前進のときのまま（狙いを選び直してよく、狙いを向く）。
5. **回り込みを終える**：下のどれかに当たったら、`detourX` を `null` に、`detourTicks` を 0 に、`advMoves` を空にして、その刻みはふつうの決まりで動く。
   - 自分の x が `detourX` に着いた（差が 1e-9 以下）。許容の幅は付けない（手前で終えると、端の守り手との横の差が `spacing` を割り、前へ出るときにまたぶつかるため）。ほかの部隊に押されて出口を越えたときは、出口まで戻ってから終える（出口の向きを状態に持たないので、「越えた」は見分けない）。
   - その刻みが、前へ進む動きでない（戦う・撃つ・堅守や後退の号令がかかった・狙いがない）。突撃の号令がかかった場合と、突撃が終わって方針が前進に戻った場合は、前へ進む動きのままなので、続ける。
   - `detourTicks` が `detourMaxTicks`（100 刻み = 10 秒）に達している。
   - 出口に着いたあとは、ふつうの前進になる。狙いが並びの内側にあると、端の守り手に斜めに当たることがあるが、相手は1部隊なので、④-2 の決まりで外側を回って前へ出る。出口に着けずに終えた場合は、5 秒後にもう一度判定する。
6. **1刻みの中の順番**（部隊ごと。判断は刻みの初めの写しで行い、動きは全部隊を同時に適用する、といういまの作りのまま）：
   1. ふつうの決まりで判断する（戦うか、撃つか、どう動くか）。ここで「前へ進む動き」かどうかが決まる。
   2. `detourX` が入っていれば、5 の終える条件を見る。終えないなら、動きたい分を真横に置き換え、`detourTicks` を 1 増やす。
   3. `detourX` が入っていなければ（2 で終えた刻みを除く）、前へ進む動きのときだけ 2 の判定をする。ふさがれていて、開いている出口があれば、4 を始め、この刻みから真横に動く（`detourTicks` は 1 になる）。
   4. 全部隊を同時に動かし、重なりをほどき、戦場と城壁に収める（いまのまま）。
   5. `advMoves` を 1 のとおりに更新する。
7. **状態**：`Unit` に `advMoves: [number, number][]`、`detourX: number | null`、`detourTicks: number` を足す（JSON にできる値だけ）。保存しておいた古い状態にこれらがないときは、空・`null`・0 として扱う（サーバーの戦闘の途中で新しい engine に替わっても落ちない）。`viewFor` と出来事には出さない。
8. **数字**：`detourStuckTicks` 50、`detourStuckDist` 0.3、`detourMaxTicks` 100、`detourReach` 0.1、`detourGap` 0.05 を `tuning.ts` に足す。**いまある数字は変えない**。

**5 秒待つ理由**

- 盾兵（守備）の後ろに弓兵（前進）を置く形（1-3 の見本、鶴翼）で、敵が近づいてくる間に弓兵が盾の陰から出てしまわないようにする。弓兵は、撃てる相手（`archerRange` 以内）が来れば止まって撃つので、「前へ進む動き」でなくなり、`advMoves` が空になる。
- 敵が守備で近づいてこないときは、5 秒待ってから回り込む。これが 1-2 と、3-2 に鶴翼を置いた場合の直しになる。
- 設計のレビューでの試作では、15面の見本（見本の号令つき）× 種20個で、この決まりが働いた回数は 0 だった。

**出口がない形**（戦場の端から端まで守備が並ぶ、谷の幅いっぱいに並ぶ、方円の内側にいる）では、回り込みを始めず、いまと同じく、その場にとどまる。城壁のそばなど、開いていると判定した出口に着けない形では、10 秒で打ち切って 5 秒待つことをくり返す。いまより悪くならないこと（下がっていかない、重なりの決まりを破らない）を条件にする。

### 3.7 ひな形と陣形名

ひな形は、手持ちの部隊（兵種ごとの数）と配置エリアを受け取って、配置と方針を返す関数。部隊の数が 6〜16 のどれでも、エリアに収まり、重ならず、全部隊を使い切ること。同じ入力からは、いつも同じ配置を返す。

**ひな形は段階1で作る**（合格条件の総当たりに使うため）。陣形名の判定は段階2で作る。

| id | 名前 | 形（自軍から見て。上が敵） | 兵種の割り当てと方針 |
|---|---|---|---|
| `line` | 横陣 | 横一列に2段 | 前列に盾兵と歩兵（前進）、後列に弓兵、両端に騎兵（迂回） |
| `crane` | 鶴翼 | V字。両翼が前に張り出し、中央が下がる | 中央に盾兵（守備）と弓兵（守備。盾の陰から撃つ。§3.6.6 で前進から替えた）、両翼に歩兵（前進）、翼の先に騎兵（迂回） |
| `scale` | 魚鱗 | 先がとがった三角形で、中央が厚い | 先に歩兵（前進）、中に盾兵（前進）、後ろに弓兵、騎兵は後ろの両脇（前進） |
| `arrow` | 鋒矢 | 矢印。細く深い縦の列で、先が矢じり | 矢じりに騎兵（本陣狙い）と歩兵（前進）、軸に盾兵（前進）、弓兵は後ろ |
| `ring` | 方円 | 本陣を囲む輪 | 外側に盾兵と歩兵（守備）、内側に弓兵（守備）、騎兵は輪の中（守備） |
| `crescent` | 偃月 | 弓なり。中央が前に出て、両翼が下がる | 中央の前に歩兵と騎兵（前進）、両翼に盾兵（守備）、弓兵は後ろ |
| `echelon` | 雁行 | 斜めの段々 | 前の段から歩兵（前進）、盾兵（前進）、弓兵。騎兵は前に出た側の端（迂回） |

- 本陣は、どのひな形でも後ろの中央（方円は輪の中心）。
- 兵種が足りない・余るときは、役割の近い兵種で埋める（盾兵 ↔ 歩兵、騎兵 → 歩兵、弓兵 → 歩兵の後ろ）。
- **陣形名の判定**：本陣を除いた配置のマスの集合 P と、同じ手持ちで作った各ひな形のマスの集合 T を比べる。横に ±2、縦に ±1 ずらした中で、`|P∩T| ÷ max(|P|, |T|)` がいちばん大きい値を、そのひな形の点とする。点が 0.75 以上で、2番目との差が 0.05 以上あるひな形の名前を返す。兵種と方針は見ない。雁行は左右どちら向きも同じ名前にする。

### 3.8 地形（段階4）

部隊の地形は、中心があるマスで決める。**地形の判定（速さ、倍率、突入の可否、弓の届く距離、柵の正面）は、すべて刻みの初めの位置と向きで行う**（§3.1）。数字は初期値で、下の「地形の条件」を満たすように調整してよい。

**平地だけの戦いは、地形を入れる前と1刻みも変わらないこと。** 地形のために、§3.5・§3.6 の数字とひな形の中身を変えない。

#### 地形の効果

| 地形 | 効果（初期値） |

| 丘 | 高低は「丘のマスにいるか、いないか」の2段だけ。丘のマスにいる間の速さ 0.85 倍。丘の上の弓兵は、届く距離 +1.5 |
| 森 | 森のマスにいる間の速さ 0.8 倍（騎兵は 0.5 倍） |
| 川 | 川のマスにいる間の速さ 0.5 倍 |
| 柵 | 柵のマスにいる間の速さ 0.4 倍 |
| 城壁 | どの部隊も入れない。弓は越える（城壁の上から撃ち合うことを、こう表す） |

損害の倍率は、§3.6.2 の表の「地形」の行に、次のとおり入る。

| | 近接 | 弓 | 騎兵の突入 |
|---|---|---|---|
| 攻める側が丘の上、受ける側が丘の外 | 1.2 | なし | なし |
| 攻める側が丘の外、受ける側が丘の上 | 0.85 | なし | なし |
| 攻める側が川の中 | 0.7 | なし | 突入は起きない |

- 盾兵の正面と柵は、両方かける。
- 突入が起きなかったときも、助走は 0 に戻る。

#### 城壁と門

城壁は、通り道と押し合いの決まりを複雑にするので、**使い方を1つの形に絞る**。

- 城壁は、戦場を端から端まで横切る1行としてだけ置く。その行のうち1マスだけを平地にして、そこに門を置く。この形は、1つの戦場に1つまで（砦攻めの面で使う）。
- 谷のような狭い場所は、城壁を使わず、**戦場の幅そのものを狭くして**表す（画面では、戦場の外側に岩壁の絵を描く）。

**城壁に入らない**

- 部隊の中心は、城壁のマスから 0.45 より内側に入らない（戦場の端と同じ扱い）。§3.6④ の最後の「戦場の内側に収める」と同じ所で、城壁のマスからも押し出す。動き・接線に沿った滑り・重なりをほどく処理のあとで、必ずこれを行う。部隊どうしの間隔と両立しないときは、城壁に入らないほうを優先する。
- 城壁の行は厚さ1マスなので、両側の部隊の中心は 1.9 以上離れる。城壁ごしに近接で戦うことはない。
- 敗走中の部隊だけは、城壁をすり抜けて逃げる（5秒で消える）。後退の号令で下がる部隊は、城壁に当たったら、そこで止まる。

**門**

- 門は、配置（`Placement`）の兵種としては扱わない。`BattleSetup.gate` で指定する：`{ side: Side; col: number; row: number; win: boolean }`。利用者が送る配置に門を入れることはできない（`validateArmy` は、知らない兵種として落とす）。
- 門は、守る側の部隊として戦場に立つ（`Unit.kind` は `'gate'`）。動かない、攻撃しない、向きを変えない。士気は 100 のまま変わらず、敗走しない。耐久（`men`）は 150。
- ほかの部隊と同じように場所を取る（中心どうし 0.9）。切れ目の幅は1マスなので、門が立っている間は、敵も味方も通れない。
- **門が破れると、両隣の城壁も崩れる**：刻み t に門が全滅したら、門のマスの左右1マスずつの城壁を平地に変える（状態の中の地形を書き換える）。刻み t+1 から、3マスの幅で通れる。切れ目が1マスのままだと、後ろの部隊が長く詰まるため。
- **門は、少し離れた所からも攻められる**：門を攻めるときだけ、近接が届く距離を 1.6 にする。門の前に3部隊ほどが並んで攻められる（1マスの切れ目の正面には、1部隊しか立てないため）。
- 受ける損害：近接だけ。`攻撃 × √(兵数の割合) × ばらつき × 攻める側の倍率（突撃の号令、丘、川）`。向きの倍率、受ける側の倍率はかけない。弓の損害は受けない（弓兵は門を狙わない）。騎兵の突入は受けない。
- 号令はかからない。味方の支え・囲み・本陣の支えには数えない。門が全滅しても、まわりの士気は動かない。「最初に消えた部隊」と、敗走させた数にも数えない。
- 「本陣以外の部隊がすべて消えた」の判定、部隊数の上限、残った兵の割合（時間切れの比べ方、星）には、門を数えない。

**通り道**（城壁のある戦場だけ）

- 部隊と行き先（狙い、持ち場、迂回の通過点、敵の本陣）が、城壁の行をはさんで反対側にあるとき、まっすぐ行き先へ向かう代わりに、次の順で進む：①門のマスの、自分の側の1マス手前の中心 → ②門のマスの中心 → ③行き先。①は、門のマスの中心から x の差が 0.3 以内で、城壁の行のすぐ隣の行にいれば、済んだものとする。
- 城壁のない戦場と、行き先が同じ側にあるときは、今までと同じ動きをする。
- 前進の狙いを選ぶときの「距離」は、反対側の敵については、門のマスの中心を通る折れ線の長さを使う。
- **門が立っている間**、反対側に狙いを持つ前進の部隊は、狙いを門に替える（門を破らないと先へ進めない）。門が近接の距離に入ったら、門と戦う。ただし、近接の距離にふつうの敵がいるときは、§3.6.1 のとおり、その敵と戦う（門より先に、目の前の敵）。
- 本陣狙いの部隊は、門の前で止められて、§3.6.1 の「詰まったとき」の決まりで門と戦う。迂回の部隊は、①②を自分の側だけで行い、③で前進と同じになる。守備の部隊は、持ち場を動かない。
- 門を攻める側は陣営0とは限らないが、面のデータでは、門はいつも陣営1のもの。

**決着**（§3.6.4 に足す）

- `BattleSetup.gate.win` が true のとき、門が全滅した刻みに、門の側の陣営は「負けの条件」を満たす（理由は `gate`）。本陣・壊滅の条件と同じ扱いで、同じ刻みに相手も負けの条件を満たしていたら引き分け。理由の優先は、`gate`、`hq`、`wipeout` の順。
- `win` が true の戦場でも、本陣を討つ・壊滅させるの決着はふつうに起きる。
- `win` が false なら、門が破れても決着しない（通れるようになるだけ）。
- この項目は `BattleState` にも持ち、JSON にして戻しても変わらない。

#### 面のデータ（§3.10 に足す）

- `seconds?: number`：面の長さ。省略すると 180 秒。
- `gate?: { col: number; row: number }`：門の場所。`win` が `gate` の面では必須。
- 戦場の大きさ：縦は 16 のまま。横は 6〜12 で、面ごとに決めてよい。配置エリアも同じ幅になる。**ひな形は、幅 6〜12 のどれでも、全部隊を重ならずに置けること**（入りきらない部隊は、後ろの行へ送る）。
- 敵の配置エリア（`field.zones[1]`）は、面ごとに広げてよい（中間地帯まで含めるなど）。敵の配置は「エリアの中」の検査だけを外し、兵種・方針・本陣1つ・部隊数の上限（本陣を含めて16）は、自軍と同じに調べる。**自軍と敵軍のマスの重なりも調べる**。城壁のマスには、どちらも置けない。
- 自軍の配置エリアには、城壁を置かない（丘・森・川・柵は置いてよい）。
- 霧（`fog`）：配置中だけ。霧のマスにいる敵は見せない。開戦したら、全部見える。

#### 地形の条件

場面は §3.9 の共通の決まりに従う。座標・地形の置き方・見る時刻は、テストを書くときに固定し、コメントに書く。比べる2つの場面は、地形のほかを同じにする。

**倍率と決まりを、小さな場面でじかに確かめる**（勝ち負けではなく、値を見る）

- 上の表の各行について、1刻みの損害が、平地の同じ場面の損害 × 表の倍率になること（ばらつきを除いて）。かからない組み合わせ（丘の上からの弓、丘への突入など）で、かかっていないこと。
- 速さ：丘・森（騎兵とそれ以外）・川・柵で、1刻みに動く距離が倍率どおりであること。
- 弓の届く距離：丘の上の弓兵は +1.5 の距離の敵を撃ち、丘の外の弓兵は撃たない。
- 突入：受ける側が森・攻める側が森・攻める側が川・柵の正面、で `impact` の出来事が出ない。柵の側面からは出る。
- 柵：側面・背面から、また攻める側も柵のマスにいるとき、倍率がかからない。
- 門：弓と突入で耐久が減らない／向きと受ける側の倍率がかからない／全滅しても両軍の士気が動かない／全滅した次の刻みから通れる／残った兵の割合に入らない。
- 地形の判定が刻みの初めの位置で行われる：その刻みに川から出た部隊は、その刻みの損害では川の中として扱われる。

- **直し方**：敵の歩兵を前進にする（騎兵が先に当たり、歩兵があとから来る）。敵の部隊の数・位置は、下の条件を満たすように決め直してよい。**変えないもの**：自軍の手持ち（本陣1・歩兵5・盾兵3）、選べる操作（方針・号令・ひな形は出さない）、手がかりの文、戦場（標準の平原）、`tuning.ts` の数字。

- **受けている配置**：敵の騎兵のいる3列のすべてで、自軍のいちばん前（行がいちばん小さい）の部隊が盾兵である配置。**受けていない配置**：その3列のどれでも、いちばん前の部隊が盾兵でない（歩兵か本陣が前にいるか、その列に誰もいない）配置。3列のうち1列か2列だけ受けている配置は、どちらにも数えない（条件を付けない）。

## 4. server（段階3）

### 4.1 作り

- Worker が `/api/*` を受け、それ以外は client の静的ファイルを返す。
- 部屋1つを Durable Object 1つが受け持つ（SQLite バックエンド）。部屋のコード（4桁の数字）から `idFromName` で引く。
- WebSocket は Hibernation API（`ctx.acceptWebSocket`）で受ける。部屋が動いていない間は、Durable Object が眠れる。
- `compatibility_date` は `2026-11-01`。
- Origin の確認と、メッセージの大きさ・頻度の上限は、超富豪の server と同じ考え方で入れる。

### 4.2 通信の方式

**サーバーが engine を刻み、席ごとに見える場面を送る。** 各自の端末で同じ計算を並行して走らせる方式は採らない。理由は2つ：相手の方針を端末に送らずに済むこと、戦闘の途中で戻った人にその時点の場面を渡せば済むこと。

**戦闘の刻み方**

- 戦闘中は `setInterval`（100ms）で刻む。戦闘の時計は `clockBase`（刻み0にあたる実時刻）で持ち、呼ばれるたびに `(今 − clockBase) ÷ 100ms` と `state.tick` の差だけ `step` を呼ぶ。1回の呼び出しで最大5刻み。
- それでも 0.5 秒より大きく遅れているときは、追いかけず、`clockBase` を今に合わせ直す（その分、戦闘が止まっていたことにする）。小さな遅れは吸収し、大きな中断は戦闘の一時停止として扱う。
- 号令は、届いた次の `step` に渡す。
- 場面（`snap`）は2刻みごと（毎秒5回）に、席ごとに `viewFor` を通して送る。**出来事は、前の `snap` のあとに起きた分をためて、まとめて送る**（奇数の刻みの出来事を落とさない）。決着した刻みは、2刻みを待たずにすぐ送る。
- 決着したら `setInterval` を止める（止めないと Durable Object が眠れない）。

**保存と再開**

- Durable Object のメモリは、眠ったり作り直されたりすると消える。**部屋の状態は、変わるたびに保存領域へ書く**（下の `RoomState`）。コンストラクタで読み戻し、つながっている WebSocket を `ctx.getWebSockets()` と添付データ（席の番号と接続の番号）から組み立て直す。
- 戦闘の状態（engine の `BattleState`）は、別の鍵で、20刻みごと（2秒ごと）・号令を受け付けた `step` の直後・決着時に書く。号令を使った回数が巻き戻らないようにするため。保存が要る刻みでは、保存してから場面を送る（相手に見せた号令が、復帰後に巻き戻らないようにする）。
- 書き込みの数を抑える：無料プランには、書き込みが1日10万行までという枠もある。最長の1戦（3分）で約140行で、1日に約700戦ぶん。見張りの時刻と「アラームを入れた時刻」は、保存せずメモリにだけ持つ。
- 号令が届いてから次の `step` までの間（最長 0.1 秒）に Durable Object が消えると、その号令は失われる。その場合、相手にも表示されておらず、回数も減っていないので、食い違いは起きない。
- 作り直されたあとの再開：保存した刻みから続ける。`clockBase` は「今 − 保存した刻み × 100ms」に合わせ直す。追いかけない。
- **見張りのアラーム**：戦闘中は、10秒先にアラームを入れ続ける（延ばすのは、戦闘の保存と同じ機会に、残りが半分を切ったときだけ）。アラームが鳴ったときに `setInterval` が動いていなければ（作り直された直後）、戦闘を再開する。誰もつながっていなくても、戦闘は最後まで進む。

**期限**

- 配置の制限時間、公開から開戦までの間、不在の判定、予約の期限、部屋の片付け、見張りは、アラーム（`setAlarm`）で扱う。期限は `RoomState` に時刻で持ち、いちばん近いものをアラームに入れる。
- アラームの候補は、段階で絞る（予約は予約中、配置の期限は配置中、公開は公開中、不在は結果の間、片付けは戦闘以外、見張りは戦闘中だけ）。次に入れる時刻が今以前になる場合は、入れずに記録を残す（過ぎた期限が残って、アラームが鳴り続けるのを防ぐ）。
- アラームは2回以上呼ばれることがある。アラームの処理は「今の時刻と、保存してある期限と、今の段階」だけを見て進め、**何回呼ばれても、段階の移り変わりと成績の加算が1回だけになる**ようにする（移る前に段階と戦闘の番号を確かめる）。

> Cloudflare の公式資料で確かめたこと（2026-11-16）：
> - `setInterval` が動いている間、Durable Object は眠らず、実行時間が課金の対象になる。無料プランの枠は1日 13,000 GB-秒で、128MB の Durable Object が1日に約28時間動ける計算になる。1戦は最長3分なので、友達どうしで遊ぶ量なら足りる。
> - `compatibility_date` が `2026-10-01` 以降なら、動いている `setInterval` が、接続のない間も Durable Object の追い出しを防ぐ（1つの操作につき最長15分）。
> - 眠るとメモリの中身は捨てられる。WebSocket ごとの添付データは残る。
> - アラームは少なくとも1回の実行が保証され、失敗すると再試行される。
> - 受け取る WebSocket のメッセージは、20通で1リクエストと数える。送るほうは数えない。

### 4.3 部屋の状態と流れ

```ts
interface RoomState {
  gen: number;                 // 部屋の世代。部屋を作るたびに乱数で決める
  phase: 'reserved' | 'waiting' | 'setup' | 'reveal' | 'battle' | 'result';   // 部屋がないことは、記録がないことで表す
  battleNo: number;            // この部屋で何戦目か
  seats: [Seat | null, Seat | null];
  score: [number, number, number];        // 陣営0の勝ち、陣営1の勝ち、引き分け
  map: string;                 // 戦場の id
  deadlines: { setup?: number; reveal?: number; reserve?: number; idle?: number; away?: number };
  rematch: [boolean, boolean];
  lastResult?: BattleSummary;
}
interface Seat {
  pid: string; name: string;
  conn: number | null;         // いま有効な接続の番号。切れていれば null
  goneSince: number | null;    // 切れた時刻
  ready: boolean;
  draft: Placement[] | null;       // 最後に届いた下書き
  lastValid: Placement[] | null;   // 最後に検査を通った下書き
}
```

```
empty → reserved（作った人の接続待ち）→ waiting（1人）→ setup（配置。120秒）→ reveal（公開。3秒）→ battle（最長180秒）→ result → setup …
```

- **部屋を作る**：`POST /api/rooms`（本文に `pid`）。Worker が4桁のコードを乱数で選び、その Durable Object に「作成」を頼む。Durable Object は、記録がないときだけ、`gen` を乱数で決めて `reserved` にし、作った人の `pid` を覚える（空きの確認と予約を、1回の処理で行う）。空いていなければ断り、Worker が別のコードで最大8回やり直す。それでもだめなら「混み合っています」を返す。予約は60秒で切れ、記録を消す。
- **入る**：`GET /api/rooms/:code/ws?pid=…&name=…`。
  - `reserved` で、`pid` が作った人のものなら、陣営0の席に着いて `waiting` へ。
  - 席にいる `pid` なら、その席に戻る。
  - 空いた席があれば、そこに着く。2人そろったら `setup` へ。
  - それ以外（部屋がない、満員）は断る。
- **1つの席に有効な接続は1つ**。同じ `pid` で新しくつなぐと、古い接続を閉じて入れ替える。古い接続の「切れた」という知らせは、接続の番号が今のものと違えば無視する。
- `pid` は、端末が作る128ビットの乱数（16進の文字列）。席に戻るための合言葉として扱い、相手には送らない。
- 部屋を作った人が陣営0、入った人が陣営1。どちらの画面でも自軍が下に見えるように、client が上下左右を返して描く。
- **`setup`**：戦場を、対戦用の4つ（§3.8）からランダムに選び、期限を決める。client は、配置が変わるたびに下書きを送る（0.5秒に1回まで）。「完了」で確定し、確定中の下書きは受け付けない（取り消せば、また受け付ける）。2人とも確定するか、期限が来たら `reveal` へ。確定していない人は、最後に検査を通った下書きを使う。それもなければ、既定の編成（`PVP_RULES.standardRoster`：本陣1・歩兵5・盾兵3・騎兵2・弓兵3。値段は予算ちょうどの 36）を横陣で並べる。合格条件で使う R15（騎兵3）は値段が 40 で、予算を超えるので使わない。
- **`reveal`**：両軍の配置（方針を除く）を両者に送る。3秒後に `battle` へ。`battleNo` を増やす。
- **`battle`**：号令を受け付ける。切れている人の部隊はそのまま戦う。戻ってきた人には、`room` と、その時点の `snap` を送る。
- **`result`**：勝敗を成績に足し、`result` を送る。両者が「もう一戦」を押すと `setup` へ。
- **不在**：`result` の間、切れてから60秒以上たった席は空ける。`result` に入った時点ですでに60秒以上の席も、`result` の途中で60秒に達した席も同じ。席が空いたら、成績を消して `waiting` に戻し、残った人に「相手を待っています」と出す。2人ともいなければ、下の片付けに任せる。
- **片付け**：誰もつながっていない状態が10分続いたら、保存した内容とアラームをすべて消す（`deleteAll`）。何も残さない。
- **回数の上限**：送信元の IP ごとに、部屋の作成は1分に10回、入室の試みは1分に30回まで（Cloudflare の Rate Limiting の binding。超えたら 429）。4桁のコードの総当たりと、作成の連打を抑える。数え方はおおよそで、拠点ごと。
- **違反した接続は閉じる**：バイナリ、大きすぎるメッセージ（4096文字超）は、すぐ閉じる。頻度は、ためておける分（20通）を使い切ったあと、さらに20通届いたら閉じる。閉じた席は「切れた」になり、同じ `pid` で入り直せる。

### 4.4 メッセージ

型は `packages/server/src/protocol.ts` に置き、client が型だけを読み込む。

| 向き | 種類 | 中身 |
|---|---|---|
| S→C | `room` | 段階、`battleNo`、席（名前・接続中か・確定したか。`pid` は含めない）、成績、期限の時刻、自分の陣営、戦場、予算 |
| S→C | `reveal` | 両軍の配置（相手の方針なし）、開戦の時刻 |
| S→C | `snap` | `battleNo`、刻み、部隊の一覧（詰めた配列）、門（あれば）、前の `snap` のあとの出来事、その先頭の通し番号（`evBase`）、残りの号令 |
| S→C | `result` | `battleNo`、勝者、理由、振り返り、成績 |
| S→C | `error` | 理由（部屋がない、満員、配置が不正、号令が不正） |
| C→S | `draft` | 配置の下書き |
| C→S | `ready` / `unready` | 配置の確定と取り消し |
| C→S | `order` | `battleNo`、相手（翼）、号令の種類 |
| C→S | `rematch` | `battleNo` |

- **受け付ける段階**：`draft`・`ready`・`unready` は `setup` だけ。`order` は `battle` で、`battleNo` が今のものと同じときだけ。`rematch` は `result` で、`battleNo` が同じときだけ。それ以外は黙って捨てる（前の戦いから遅れて届いたメッセージが、今の戦いに効かないようにする）。
- 配置はサーバーが `validateArmy` で検査する（自分のエリア内、重なりなし、本陣1つ、予算内、部隊数の上限）。
- 対戦の配置は、どちらの席も「自分が下」の座標で送る。サーバーが、陣営1のぶんを上下左右に返して戦場の座標にする。場面を陣営1に送るときも、同じように返す（左翼・右翼も、自分から見た向きになる）。
- `evBase` は、その戦いの最初から数えて、この `snap` の出来事の先頭が何番目かを表す。サーバーが作り直されると、保存した時点より後の出来事が、もう一度送られることがある。client は、番号には頼らず、「刻みと中身が同じ出来事を何回渡したか」で重複を見分ける（作り直しのあいだに新しい号令が入ると、番号がずれるため）。
- 門は、部隊の一覧には入れず、`BattleView.gate` と同じ中身（場所・耐久・状態）で別に送る。
- 相手に送るものに、相手の方針・狙い・下書き・`pid` を含めない。通しのテストで、陣営1に届いた全メッセージを調べ、陣営0の方針が含まれていないことを確かめる。

### 5.2 戦闘を映す仕組み

```ts
interface BattleSource {
  onFrame(cb: (frame: { tick: number; view: BattleView; events: BattleEvent[] }) => void): void;
  onEnd(cb: (summary: BattleSummary) => void): void;      // 決着したときの振り返り
  order(target: OrderTarget, kind: OrderKind): void;
  canOrder(target: OrderTarget, kind: OrderKind): boolean;  // まだ渡していない号令のぶんも数に入れる
  setSpeed?(mult: number): void;       // 1人用だけ。ないときは、早送りのボタンを出さない
  dispose(): void;
}
```

- 戦闘の画面は、`BattleSource`・戦場・見る側の陣営（`viewer`）を、開始時に受け取る。自軍かどうか、残りの号令、色、号令の相手は、すべて `viewer` で決める。`viewer` が 1 なら、上下左右を返して自軍を下に映す。
- 翼の呼び方は、いつも見ている人から見た左右にする。engine は、その陣営から見た左右で翼を持つので、敵軍の翼は左右を入れ替えて表示する。

- `LocalBattleSource`：ブラウザで engine を動かす。実時間をためて 0.1 秒ごとに `step` を呼ぶ（早送りは2倍ためる）。場面は2刻みごとに出す（対戦と同じ見え方にする）。
- `RemoteBattleSource`：サーバーの `snap` をそのまま流す。
- どちらも、出来事は「前の場面のあとに起きた分」をまとめて渡す。決着した刻みは、2刻みを待たずにすぐ出す。
- 戦闘の画面は `BattleSource` だけを見る。前の場面と今の場面のあいだを、時間で補って描く。
- 部隊の描き方は「戦場の座標 → 画面の座標」の変換を1か所（`FieldView`）に閉じ込める。段階5の斜め視点は、この変換と絵の組を差し替えて足す。

### 5.3 見た目

- ドット絵。1マス 24px。部隊は、兵数に応じた数の小さな兵（歩兵・盾兵・弓兵は最大9人、騎兵は最大4騎、本陣は将1人と護衛4人）と、兵種を示す旗で描く。兵が減ると、描く兵も減る。部隊の絵は、回転しても隣の部隊と重ならないよう、中心から半径 10px に収める（最初は最大16人としたが、その大きさに16人を入れると、兵種を見分けられなかった）。
- 陣営の色は2色（自軍と敵軍）。対戦でも、自分がいつも同じ色で下にいる。
- 士気は、旗の高さで示す（下がるほど旗が下がる）。数字や棒は常には出さない。部隊を押している間だけ、兵数と士気を出す。
- 画面の内部の大きさは、縦長（スマホ）が 320 × 568 以上、横長（PC）が 640 × 400。戦場（288 × 384）は同じ大きさで描き、操作の欄を、縦長では下に、横長では右に置く。拡大は Phaser の FIT に任せる。
- 文字は DotGothic16 の 16px と 32px だけ。平らな塗り、2px 単位の枠。グラデーション・ぼかした影・光彩・角丸は使わない。
- 絵は、ドットの並びを書いたデータから、起動時にテクスチャを作る（画像ファイルを置かない）。段階1は、色のついた四角と点の仮の絵でよい。
- 音は効果音だけ。WebAudio で合成する（太鼓、ぶつかる音、敗走、勝ち負け）。音のファイルは置かない。最初の操作で音を解禁する。

`localStorage` に、1つのキー（`jinkei-gassen/v1`）で JSON を置く：面ごとの最高の星、名前、`pid`、保存した陣形（段階5）。読み書きは try/catch で包み、使えなくても遊べるようにする。

### 5.6 陣形の保存（段階5）

- 配置の画面に「保存」と「呼び出す」を置く。ひな形と同じ並びに置き、ひな形を出さない面（1-1〜1-3）では出さない。
- **保存**：いまの配置に名前（1〜8文字）を付けて残す。8つまで。いっぱいのときは、どれと入れ替えるかを選ぶ。同じ名前があれば上書きする。
- **持つもの**：名前、配置（配置エリアの左上を原点にした列と行、兵種、方針）、配置エリアの幅。保存の鍵（`jinkei-gassen/v1`）の `formations` に置く。
- **呼び出す**：一覧から選ぶと、いまの配置を置き換える。一覧には、名前と、小さな配置の絵（マスの点）を出す。消すこともできる（2回押して確定）。
- **合わないときの扱い**（1人用）：保存した順に置いていき、その面の手持ちを超える兵種の部隊、配置エリアの外になる部隊、置けないマスの部隊は、置かずに飛ばす。その面で選べない方針は、兵種の初期設定に直す。飛ばした部隊があれば「置けない部隊を除きました」と1行出す。手持ちが余っても、足さない（手で置く）。
- **対戦**：保存した配置の編成を、そのまま編成にする。予算を超える場合は、後ろの部隊から外して収める。
- 1人用で保存した陣形を対戦で、対戦で保存した陣形を1人用で、どちらも呼び出せる。

### 5.7 斜め見下ろしの視点（段階5）

- 戦闘の画面にだけ「視点」のボタンを置き、真上と斜めを切り替える。配置・公開・結果は、真上のまま。選んだ視点は保存する。
- 斜めは、遠近をつけない平行な投影：横はそのまま、縦を 0.6 倍に縮める（1マスが 24 × 14px ほどの平たい形に見える）。戦場の絵（地形のタイル）も同じ比で縮めて描く。縦が縮んで空いた分は、戦場を縦の中央に寄せる。
- 兵は、**立った姿の絵**に替える（真上の絵を縮めるのではなく、斜め上から見た、頭と体と足が見える絵。兵種の見分けは、真上と同じ手がかり：槍、盾、馬、弓、将と大きな旗）。向きは4方向、歩きは2コマ。旗は、真上より高く立てる。
- 部隊の中の兵の並びは、戦場の座標で決めてから投影する（奥の兵ほど上に、手前の兵ほど下に描かれる）。**奥のものから先に描く**（部隊どうしも、兵どうしも、門・柵・森の木も、画面の縦の位置の順）。森の木・柵・城壁・門は、斜めのときだけ、少し高さのある絵にする。
- 演出（火花、土煙、矢、崩れる門、霧）と、部隊を押して数字を出す操作、号令の相手の枠は、斜めでも同じに働く。押した位置から戦場の座標へ戻す計算も、`FieldView` に持たせる。
- 真上と斜めで、戦闘の中身（場面と出来事）は同じ。切り替えは、戦闘の途中でいつでもできる。

### 5.8 横からの視点と将軍の視点（issue #1。decisions §14）

戦闘の画面の視点を4つにする：真上（`top`）・斜め（`oblique`）・横から（`side`）・将軍（`general`）。
戦闘の中身（場面と出来事）、操作、隠す情報は、どの視点でも同じ。変わるのは「戦場の座標 → 画面の座標」の変換と、使う絵だけ。

#### 5.8.1 共通の作り

- 視点の型は `ViewMode = 'top' | 'oblique' | 'side' | 'general'`。`FieldView` は `oblique: boolean` の代わりに `mode: ViewMode` を持つ。
- 視点で分かれる計算は、すべて `FieldView` に入れる。シーンや絵の側は `fv.mode` を見て分けない。いま `fv.oblique` や `this.oblique` で分けている所は、下の表のとおり `FieldView` の値に置き換える。

| いまの分け方（場所） | 置き換え |
|---|---|
| `toScreen` / `toField` / `cellAt`（FieldView） | 視点ごとの変換（§5.8.2、§5.8.3） |
| `dirToScreen`、兵の並びを回して縦だけ縮める計算（UnitSprite.apply の `yScale`） | `fv.vecToScreen(x, y, vx, vy)`：戦場の座標 (x, y) にある、戦場の向きと長さ（マス単位）のベクトルを、画面の px のベクトルに直す。兵の並び（lx, ly は px で書いてあるので 1/CELL してから渡す）と、部隊の向き（4方向の絵を選ぶ）の両方をこれで決める |
| 立った兵の絵にするか（UnitSprite の `oblique`、`keyOf`） | `fv.standing`（真上だけ false） |
| 兵の絵の倍率 | `fv.spriteScale(x, y)`（整数。将軍の視点だけ 1 以外になる） |
| 奥のものから描く並べ替え（BattleScene `soldierLayer.sort('depth')`、UnitSprite の `setDepth`、門・木・柵・城壁の `setDepth`） | `fv.depthSorted`（真上だけ false）と `fv.depthOf(x, y)`（戦場の座標 → 並べる値。画面で手前のものほど大きい） |
| 押した位置のずらし（BattleScene.onDown の `+6`）、数字の箱の持ち上げ（drawInfo の 34 / 20）、旗の高さ（UnitSprite.drawMarks）、号令の印の位置 | `fv.standing` と `fv.spriteScale` から決める（立った絵の高さ × 倍率） |
| 旗・箱・押せる範囲を止める矩形（BattleScene.clipRect） | `fv.clip(area)`：真上は戦場の矩形。ほかは、縦を描き場所いっぱいまで広げる。横から・将軍は横も描き場所いっぱい |
| 地形のタイルを敷く（art/field.ts `addFieldImage`）、霧のマス、瓦礫、号令の相手の枠 | `fv.cellQuad(col, row)`：マスの4隅の画面の座標。真上・斜め・横からは軸に平行な矩形なので、いまの `cellRect` も残す（矩形でない視点で `cellRect` を呼んだら、4隅を囲む矩形を返す）。タイルは §5.8.4 のとおり敷く |
| 高さのある絵（木・柵・城壁・門。BattleScene.buildTallTerrain、GateSprite） | `fv.standing` のとき立てる。絵は視点ごとに §5.8.4 |
| `centeredFieldView(area, field, flipped, oblique)` | 最後の引数を `mode` にする。配置・公開の画面は `top` を渡す（いまと同じ見た目） |
| 保存（save.ts の `view`、`sanitize`、`savedView`、`saveView`） | 4つの値を受け付ける。知らない値は `top` |
| 視点のボタン（BattleScene.toggleView、ボタンの文字） | 押すたびに top → oblique → side → general → top。文字は「視点：真上」「視点：斜め」「視点：横」「視点：将軍」 |

- `flipped`（陣営1の人が見るとき上下左右を返す）は、いまと同じく、視点の変換の前にかける。以下の式の (x, y) は、返したあとの座標（自軍が下＝y が大きい側）。
- 視点を切り替えても、`BattleSource` と補間は作り直さない（いまと同じ。表示物だけ作り直す）。
- 演出（火花・土煙・矢・全滅の兵・号令の旗）は、画面の座標を受け取って描くので、変換を通した座標を渡せば動く。矢の山なりは画面の縦に持ち上げる（いまと同じ）。

#### 5.8.2 横から

- 見る人は、戦場の右の辺（x が大きい側）の外から、左（x が小さい側）を向いて、少し見下ろす。自軍（y が大きい側）が画面の左、敵軍が右になる。真上の絵を時計回りに 90° 回した向きで、鏡写しにはならない。
- 変換（遠近なし）。`rows` は戦場の行の数、`cols` は列の数：
  - 画面の横 = `rect.x + (rows − y) × CELL × 0.75`（奥行きを 0.75 倍。16 行で 288px）
  - 画面の縦 = `rect.y + x × CELL × 0.6`（斜めと同じ縮み。12 列で 172.8px）
  - `rect` は、描き場所（12 列 × 16 行ぶん、288 × 384px）の中央に置く。戦場が狭い（列が少ない）ときは縦が短くなるだけで、横は変わらない。
- 1マスは 18 × 14.4px の矩形になる。`cellRect` は、いまと同じく両端を丸めてから差を取る（隙間も重なりも出さない）。
- 兵は、斜めと同じ立った姿の絵（倍率 1）。向きは、戦場の向きを画面の向きに直してから4方向を選ぶ（敵へ向かう自軍は右向き）。兵の並びも `vecToScreen` を通すので、部隊の横の並びは画面の縦に、前後の並びは画面の横に並ぶ。
- 奥のものから描く：並べる値は画面の縦（x が大きいほど手前）。
- 左翼・右翼：自軍の左翼（x が小さい側）が画面の奥（上）、右翼が手前（下）。号令の相手の枠は、対象のマスを `cellQuad` で囲むので、どの部隊が対象かは枠で分かる。
- 戦場の外（描き場所のうち戦場でない所）は、いまと同じ岩壁の絵。

#### 5.8.3 将軍

**未決**（2026-11-18、ユーザーに確認中）。合意の「兵の絵は 3・2・1 倍」と「戦場の手前が枠の幅いっぱい」は、同時には成り立たない（枠は 288px で 12 列なので手前の 1 マスは 24px。3 倍の兵の絵は 1 マスが 72px のときの大きさ）。次のどれにするかを決めてから書く。

- A：手前を切る（兵の絵は 3・2・1 倍。手前は本陣のまわり 4 列ぶんだけが枠に入り、奥は 12 列ぜんぶが入る）
- B：戦場ぜんぶを入れる（兵の絵はどこでも同じ大きさ。位置だけに遠近がつく）
- C：戦場ぜんぶを入れて、兵の絵だけ 3・2・1 倍（手前の部隊どうしが大きく重なる）

共通の作り（§5.8.1）は、遠近つきの変換を足せる形にしておく（`cellQuad`、`spriteScale`、`depthOf`、`vecToScreen`）。遠景の絵（1人用の 15 面と、対戦の地図 4 つ）は、地平線の位置と絵の大きさが決まってから作る。

#### 5.8.4 絵

- 地形のタイル：真上・斜め・横からは、マスの矩形に、タイルの絵をぼかさずに伸び縮みさせて敷く（いまの斜めと同じ）。横からでも、タイルの絵は回さない（草・丘・森の地面・川は向きの目立たない模様のため。川の流れの向きが気になるときは、横から用に 90° 回した絵を使う）。
- 高さのある絵（横から）：
  - 森の木：いまの `TALL_TREE` をそのまま、マスの中に1本（位置の互い違いは、いまと同じ決め方を画面の向きに合わせる）。
  - 柵・城壁・門：戦場では横（x の向き）に伸びるものなので、横からでは画面の奥行き（縦）に伸びる。いまの絵は「左右に伸びる壁を正面から見た絵」なので使えない。**横から用の絵**（1マスぶん：幅 18px ほど、マスの縦 14.4px に高さを足した絵。壁の小口と上の面が見える）を、いまの絵と同じ色・同じ描き方（`textures.ts` の、文字の並びから描く方式）で足す。奥のマスから順に描けば、1本の壁につながって見える。
  - 門は、壊れ具合の3段階と、破れたあとの瓦礫（平たい絵をマスに敷く）を、いまと同じに。
- 兵の絵・旗・印は、いまの斜め用をそのまま使う。新しい兵の絵は描かない。

## 7. 遊軍（issue #2。decisions §15）

手持ちの部隊から1つを控えさせ、戦闘中に1回だけ呼ぶと、戦場の端に現れる。engine・server・client のすべてに手が入るので、1つの章にまとめる。

### 7.1 原則

- **遊軍を使わない戦いは、1刻みも変わらない。** 遊軍のない設定（`reserves` を書かない、または両方 null）で作った戦いは、状態の項目が増える以外、いままでと同じ結果になる。T10（記録した20戦との一致）、A1〜A15、T1〜T9、D1〜D8、K1〜K10 は、記録も期待値も変えずに通る。
- 遊軍を呼ぶ処理は乱数を引かない。
- 呼ばれる前の遊軍は、`state.units` に入れない（部隊を走査するどの決まりにも映らない）。呼ばれた刻みに、`state.units` の末尾に足す（id は、そのときの `state.units.length`）。

### 7.2 engine の型

```ts
/** 控えさせる部隊。兵種は本陣以外 */
export interface ReserveSetup { kind: Kind; stance: Stance }
export type ReserveFrom = 'left' | 'right'; // その陣営から見た左右（翼と同じ向き）
export interface ReserveInput { side: Side; from: ReserveFrom }
export interface ScriptedReserve { tick: number; side: Side; from: ReserveFrom }

// BattleSetup に足す
reserves?: [ReserveSetup | null, ReserveSetup | null];
scriptedReserves?: ScriptedReserve[]; // 面の敵（と、見本・測定の自軍）が呼ぶ予定。陣営ごとに1つまで

// BattleState に足す
reserves: [ReserveState | null, ReserveState | null];

/**
 * used が true なら呼んだあと（unit は現れた部隊の id）。呼ぶ前は unit が null。
 * auto は予定された遊軍（なければ null）。tick になったら from から呼ぶ
 */
export interface ReserveState { kind: Kind; stance: Stance; used: boolean; unit: number | null; auto: null | { tick: number; from: ReserveFrom } }

// BattleEvent に足す
| { type: 'reserve'; tick: number; side: Side; unit: number; from: ReserveFrom }

// BattleView に足す。見る人の陣営のぶんだけ値を入れ、相手のぶんはいつも null（viewer が 'both' なら両方入れる）。
// 入れる値が1つもないとき（遊軍のない戦い、相手だけが遊軍を持つ戦い）は、項目ごと入れない（遊軍のない戦いの場面の形を、いままでと同じに保つ。A15）
reserve?: [ReserveView | null, ReserveView | null];
/** state: 'waiting' はまだ呼べない（開戦 5 秒まで）、'ready' は呼べる、'used' は呼んだあと */
export interface ReserveView { kind: Kind; stance: Stance; state: 'waiting' | 'ready' | 'used' }

// BattleSummary に足す
/** 呼ばなかった遊軍（陣営ごと。いなければ、または呼んだなら null） */
unusedReserve: [{ kind: Kind; men: number } | null, { kind: Kind; men: number } | null];
/** 星の条件に使う割合（§7.5）。呼ばなかった遊軍を、無傷で残ったものとして数える */
remainingForStars: [number, number];
```

- `T.reserveMinTick = 50`（開戦から 5 秒）を `tuning.ts` に足す。いまある数字は変えない。
- 遊軍の値の検査は、1つの関数（`reserveErrors(reserve)`）にまとめ、engine・面・server のどこからも同じものを呼ぶ：オブジェクトである、兵種が本陣以外の4つのどれか、方針が `isStance` を満たす（`stanceAllowed` は本陣以外ならいつも true を返すので、これだけでは知らない文字列を落とせない）、`stanceAllowed(kind, stance)` を満たす。誤りは `ArmyError[]` で返す（兵種の誤りは `invalid_kind`、方針の誤りは `invalid_stance`。どちらも index を付けない）。置き場所は `army.ts`。
- `createBattle` の検査：`reserves` は長さ2の配列で、要素は null か、上の検査を通るもの（undefined も正しくない）。`scriptedReserves` は配列で、陣営ごとに1つまで、その陣営に遊軍がいること、tick は 0 以上の整数、side と from が正しい値。正しくなければ `invalid_setup`。tick が `T.reserveMinTick` より小さい予定は、`T.reserveMinTick` として扱う。
- 部隊数の上限（`MAX_UNITS`）は、戦場の部隊 + 遊軍で数える。`createBattle` は、戦場の部隊の数 + 遊軍の数が上限を超えたら `invalid_army`（`too_many_units`）を返す（`validateArmy` に `limits.reserve` を渡して数える）。
- 古い状態（`reserves` のない保存された状態）は、`step` の初めに `reserves = [null, null]` として扱う（`quietTicks` と同じやり方）。

### 7.3 呼ぶ

公開する関数：

```ts
/** 遊軍を呼べるか（状態は変えない）。呼べないときは理由を返す */
export function canSummon(state: BattleState, side: Side, from: ReserveFrom): Result<true>;
/** 場面だけから、呼べそうかを判定する（対戦の画面用）。見るのは、決着していないことと、自分の遊軍が 'ready' であることだけ。現れるマスがあるかまでは分からないので、押したあとに server から no_spawn_cell が返ることがある */
export function canSummonView(view: BattleView, side: Side): boolean;
/** step に遊軍の入力を足す。省略すれば、いままでと同じ */
export function step(state: BattleState, orders: readonly OrderInput[], summons?: readonly ReserveInput[]): BattleEvent[];
```

- 呼べる条件：決着していない、その陣営に遊軍がいて `used` が false、`state.tick >= T.reserveMinTick`、現れるマスが見つかる（§7.4）。
- エラーコードを足す：`no_reserve`（遊軍がいない・呼んだあと）、`reserve_not_ready`（開戦 5 秒まで）、`no_spawn_cell`（現れるマスがない）。from が正しくなければ `invalid_order`。調べる順は、値の形（`invalid_order`）→ `battle_over` → `no_reserve` → `reserve_not_ready` → `no_spawn_cell`。
- `step` の中の順番：**①号令を受け付ける前**に、遊軍を呼ぶ（予定された遊軍を先に陣営0・陣営1の順に、続けて渡された入力を配列の順に。1刻みに受け取る入力の数の上限は号令と同じで、先頭の 8 件だけを見る。形の正しくない入力は、号令と同じく黙って捨てる）。同じ刻みに両軍が呼んだときは、この順に1つずつ現れる（先に現れた部隊は、あとの部隊の「空いているマス」の判定に入る）。
  - 先に呼ぶ理由：`moraleDelta`・`snap`・`decisions`・`anchors`・`newPos` など部隊ごとの配列を作る前に `state.units` を伸ばすため（`n` と `moraleDelta` は、遊軍を足したあとに作る。**これらを作ったあとに `state.units` を伸ばしてはいけない**）。門を末尾へ置き直す必要はない（いまある id は変わらない）。
  - 同じ刻みに engine へ渡った号令は、現れたばかりの遊軍にもかかる（全軍あて、出た側の翼あて）。ただし、号令を受け付ける側（server の `canOrder`、1人用の `LocalBattleSource`、対戦の `canOrderView`）は、**その時点で戦場にいる部隊**で調べる。だれもいない翼へ遊軍を呼び、同じ刻みにその翼あての号令を出しても、号令は受け付けられない（遊軍が現れた次の刻みから受け付ける）。この 0.1 秒の差は、そのままにする。
- 現れた部隊の値：
  - `id = state.units.length`、`side`、`kind`、`stance` は遊軍の設定どおり。`men = maxMen =` その兵種の初期値、`morale = T.moraleMax`、`status = 'active'`。
  - 位置は、現れるマスの中心。向きは、`frontOf(side)`（開戦時の部隊と同じく敵の方向）。現れた刻みの ③〜④ で、ほかの部隊と同じように狙いを決め、動き、向きを変える。
  - `wing` は、`from`（left / right）。
  - `home` は現れた位置。`flankPhase = 2`、`flankEdgeX = 現れた x`（迂回の方針なら、すでに端にいるので「端に沿って進む」から始める）。そのほかの項目（`runup`、`huntMoves`、`advMoves`、`detourX` など）は、開戦時の部隊と同じ初期値。
  - `state.initialMen[side]` に、その兵数を足す（§7.5）。
  - `state.reserves[side]` を `used: true, unit: id` にし、出来事 `{ type: 'reserve', … }` を出す。
- 呼べなかった入力は、黙って捨てる（号令と同じ。出来事を出さない）。
- 予定された遊軍（`auto`）：`state.tick >= auto.tick` で、まだ呼んでいなければ、毎刻み試す。現れるマスがなくて呼べなかったときだけ、次の刻みにもう一度試す。陣営ごとに別々に試す（片方が呼べなくても、もう片方を止めない）。人の入力で先に呼ばれたら、予定は使わない。

### 7.4 現れるマス

- 行の候補：その陣営の「中央の線のすぐ自陣側」の行から、自陣の奥へ向かって順に。陣営0（下の側）は `row = Math.ceil(height / 2)` から `height − 1` へ、陣営1（上の側）は `row = Math.floor(height / 2) − 1` から `0` へ。高さが奇数の戦場では、まん中の行はどちらの候補にもならない。両軍の候補は、戦場を 180° 回すと重なる。
- 列：その陣営から見た左右を、戦場の列に直す。陣営0の左は `col = 0`、右は `col = width − 1`。陣営1は逆（左が `width − 1`、右が `0`）。`wingOf` と同じ向き。
- 候補のマスを上の順に見て、次をすべて満たす最初のマスに現れる：
  - 城壁（`wall`）のマスでない。
  - 城壁の行がある戦場では、その行より自陣側（自分の配置エリアと同じ側）にある。城壁の行そのものと、その向こう側は候補にしない。門が破れたあとも同じ。城壁の行は `state.gate.row` で読む（門が破れると切れ目が3マスになり、城壁の形を読み直せないため）。自陣側は、行の候補と同じく、陣営0が行の大きいほう、陣営1が行の小さいほうとする。
  - マスの中心から `T.spacing`（部隊の間隔。いまの値のまま）未満の距離に、戦場にいる部隊（active と routing。門を含む）がいない。
- 見つからなければ呼べない（`no_spawn_cell`）。
- 決め方に乱数も部隊の並び順の偶然も入らない。対戦の地図は左右対称・上下対称なので、両軍の候補は鏡写しになる。
- 気をつけること（実装で分かった）：陣営0の左（列 0・行 8）と陣営1の右（列 0・行 7）は、同じ列の隣り合うマスで、中心どうしの距離 1.0 は近接の距離（`T.meleeRange` = 1.05）より短い。両軍が同じ端から呼ぶと、現れた刻みから戦いになる。

### 7.5 判定と数え方

- 時間切れと膠着（`timeoutWinner`）：いまの `remainingRatio` をそのまま使う。呼ばなかった遊軍は `state.units` にも `initialMen` にも入っていないので、数に入らない。呼んだ遊軍は、呼んだ刻みから両方に入る。
- 星（`starsFor`）：`summary.remainingForStars[side]` を読むように変える（数でない値なら、いままでと同じく星1つ）。`remainingForStars = (active な部隊の兵数の合計 + 呼ばなかった遊軍の兵数) ÷ (initialMen + 呼ばなかった遊軍の兵数)`。遊軍のない戦いでは `remaining` と同じ値になる。
- `summary.remaining` の意味は変えない（判定に使う割合）。結果の画面の「残った兵」の表示は `remainingForStars` を使う（星の数と表示が食い違わないように）。
- 全滅の判定（wipeout）と本陣の判定は変えない。戦場の部隊で決まる。呼ばなかった遊軍がいても、決着を止めない。
- 膠着の時計（`isQuietTick`）：呼ばなかった遊軍は時計を止めない。ただし、**予定された遊軍（`auto`）がまだ呼ばれていないあいだ**は、静かな刻みと数えない（予定された号令が残っているあいだと同じ扱い。面の敵が遊軍を出す前に、膠着で終わらないように）。マスがふさがって呼べない状態が続いても、戦いは時間切れで終わる。
- `starsFor` と結果の画面は、`remainingForStars` がない振り返り（古い形で保存された結果）では、`remaining` を使う。
- `summary.units` には、呼んだ遊軍が入る（`state.units` にいるので）。呼ばなかった遊軍は `summary.unusedReserve` に入る。

### 7.6 面と配置の検査（engine）

- `validateStageArmy(stage, placements, reserve?)`：`reserve` があるとき、兵種ごとの数（手持ち）と部隊数の上限を、戦場の部隊 + 遊軍で数える。遊軍の兵種が本陣なら `invalid_kind`（手持ちには数えない）、方針がその面で選べなければ `invalid_stance`（index は付けない）。本陣以外の部隊の下限（1つ以上）は、戦場の部隊だけで数える（遊軍だけ残して戦場を本陣だけにはできない）。
- `stageSetupWith(stage, placements, seed, myOrders, reserve?, myReserve?)`：`reserve` は自軍の遊軍、`myReserve` は見本・測定用の「何秒にどちらから呼ぶか」（`{ atSec, from }`）。自軍にも敵にも遊軍がなければ、`reserves` と `scriptedReserves` の項目を足さない（いままでと同じ設定を作る）。面のデータ `Stage` に、敵の遊軍 `enemyReserve?: { kind, stance, atSec, from }` を足せるようにする（いまの15面には書かない）。
- 対戦の配置の検査（予算・手持ち・部隊数）も、戦場の部隊 + 遊軍で数える。`validateArmy` の `ArmyLimits` に `reserve?: ReserveSetup | null` を足し、予算と部隊数に含める。遊軍の値が正しくないときは `reserveErrors` の誤りを足し、部隊数には1つとして数える（数の上限を、要素を調べる前に見るため）。予算は、ほかの誤りがないときだけ見る（いままでと同じ）。
- ひな形（`applyTemplate`）は遊軍を作らない。配置の画面でひな形を選んだら、遊軍の枠は空に戻す（ひな形は手持ちの全部隊を並べるので、枠を残すと二重に数えることになる）。
- `pnpm sim` の面の集計は、判定に使う割合（`remaining`）と星に使う割合（`remainingForStars`）を別々に出す。

### 7.7 server

- 受け取るメッセージ：
  - `draft` と `ready` に `reserve?: { kind, stance } | null` を足す（省略と null は「遊軍なし」）。検査は §7.6。正しくなければ、いまの配置の誤りと同じ形でエラーを返す。
  - **配置と遊軍は、いつも一組で扱う。** 下書き（`draft`）、最後に検査を通った配置（`lastValid`）、確定した配置、時間切れのときに使う配置、復帰のときに返す配置は、どれも `{ army, reserve }` の組で持ち、組ごと検査して、組ごと入れ替える（古い配置に新しい遊軍が付くことがないように）。`ready` で `army` を省略したときは、いまの下書きの組をそのまま使い、`reserve` の値は見ない。`army` を付けたときは、同じメッセージの `reserve`（省略なら「なし」）と組にする。
  - `{ type: 'reserve'; battleNo: number; from: 'left' | 'right' }` を足す。受け付けの条件は、号令と同じ作り（戦闘中だけ、battleNo が合うこと、`canSummon` を通ること、次の刻みで engine に渡す）。まだ engine に渡していない遊軍の入力は、陣営ごとに1つまで（2つ目は捨てる）。呼べないときは、エラーを本人にだけ返す。エラーには `op: 'reserve'` を付けて、号令のエラーと見分けられるようにする（client は、号令の「送って返事待ち」の数を、遊軍のエラーで減らさない）。
- **遊軍を使える部屋かどうか**：client は、つなぐときの URL に `cv=2`（遊軍を知っている版）を付ける。server は、席ごとにこれを覚え、**両方の席が `cv=2` 以上のときだけ** `room.rules.reserve = true` を送る。そうでない部屋では、`draft` / `ready` の遊軍を「この部屋では遊軍を使えない」というエラーで落とし、`reserve` のメッセージも受け付けない。古い画面（開いたままのタブ）は、途中で増えた部隊の絵を作れないため。配置の段階の途中で、古い画面の人が入り直して `cv` が変わったら、その時点の下書きの遊軍を外して、両者に `room` を送り直す。
- 送るメッセージ：
  - `room`：自分の下書きの遊軍（`myReserve`）を、自分にだけ入れる。
  - `reveal`：自分の遊軍だけ入れる。**相手の遊軍は、あるかないかも含めて入れない。**
  - `snap`：`reserve`（自分のぶんの `ReserveView`。なければ null）を足す。相手のぶんは入れない。現れた遊軍は、ふつうの部隊として `units` に入り、出来事 `reserve` が両者に届く。
  - `result`：振り返り（`summary`）の `unusedReserve` は、**相手のぶんを null にしてから**送る。`remainingForStars` も、相手のぶんは `remaining` と同じ値に置き換える（呼ばなかった遊軍がいたことを、戦いのあとも相手に知らせない）。いまは決着のときも、結果の画面に入り直したときも、同じ1つのメッセージを両者に送っているので、**見る人ごとに作って送る**形に変える。保存してある振り返りそのものは書き換えない。
- 上下を返す処理（`flip.ts`）：`from` は「その陣営から見た左右」なので返さない。現れた部隊の座標と、出来事 `reserve` は、ほかの部隊・出来事と同じに扱う。
- もう一戦に入るとき、下書きの遊軍も消す（配置と同じ）。
- 途中で落ちて戻る処理：server は入力を再生せず、保存した `BattleState` から再開する。いまは号令の出来事が出た刻みにすぐ保存し、ほかは 20 刻みごとに保存している。**遊軍が現れた刻み（出来事 `reserve`）も、すぐ保存する**（保存してから `snap` を送る）。そうしないと、相手に見せた遊軍が、落ちて戻ったときに消えて、もう一度呼べてしまう。
- 古い client（遊軍を知らない）と新しい server：上の `cv` の決まりで、古い画面のいる部屋では遊軍が使えない。通信の形は、項目が増えるだけなので、古い client でも読める。
- `snap` の `reserve` は、自分のぶんの `ReserveView`（なければ null）を1つだけ入れる。client の `RemoteBattleSource` は、これを `BattleView.reserve` の自分の側に入れ、相手の側を null にして組み立てる。

### 7.8 client

- **戦闘の途中で部隊が増える**：`BattleScene` は、場面に知らない id の部隊が出てきたら、その場で `UnitSprite` を作る（いまは最初の場面でだけ作っている）。補間（`FrameInterpolator`）は、前の場面にない部隊を、いまの位置にそのまま出す（動かさない）。
- `BattleSource` に足す：`reserve(): ReserveView | null`（自分の遊軍）、`canSummon(): boolean`、`summon(from: ReserveFrom): void`。1人用（`LocalBattleSource`）は engine をそのまま呼び、対戦（`RemoteBattleSource`）は `snap.reserve` と `canSummonView` を使ってメッセージを送る。
- 配置の画面（`DeployScene`）：
  - 手持ちの並びのそばに「遊軍」の枠を1つ。手持ちの兵種（本陣以外）を選んだ状態で枠を押すと、その兵種の1部隊が遊軍になる（手持ちの数が1つ減る）。枠に部隊が入っているとき、枠を押すと小さな箱が出て、方針の切り替えと「外す」ができる（戦場の自軍を押したときと同じ箱）。
  - 遊軍は、面ごとの最後の配置と一緒に保存する（`save.ts`：`reserves: Record<面の id, ReserveSetup>` と `pvpReserve`）。保存した陣形（`SavedFormation`）に `reserve?: ReserveSetup` を足し、呼び出したときに、手持ちに足りていれば遊軍の枠に入れる。型だけでなく、読み込みの掃除（`sanitize`）・保存・読み戻しのすべてで遊軍を扱う（いまは、決まった項目だけを写しているので、足さないと消える）。
  - 対戦では、`room.rules.reserve` が true の部屋でだけ、遊軍の枠を出す。
  - 対戦では、下書き（`draft`）と準備完了（`ready`）に遊軍を入れて送る。公開の画面（`RevealScene`）には、自分の遊軍だけを枠で見せる。相手の遊軍は出さない。
- 戦闘の画面（`BattleScene`）：
  - 号令のボタンのそばに「遊軍 左から」「遊軍 右から」。自分に遊軍がいる戦いだけ出す。`waiting`（開戦 5 秒まで）と `used`（呼んだあと）は、押せない色。
  - 出来事 `reserve` が届いたら、現れた部隊の上に「遊軍」と短く出す（号令の表示と同じ出し方・同じ長さ）。自軍でも敵軍でも出す。音は、号令の太鼓と同じ音を鳴らす（新しい音は足さない）。
  - 左右：ボタンの「左」「右」は、見ている人から見た左右（真上・斜め・将軍の視点では画面の左右と同じ。横からの視点では、左が画面の奥、右が手前）。
- 結果の画面：呼ばなかった遊軍がいたら、振り返りの部隊の並びの最後に、その兵種を「遊軍（出さず）」として出す。「残った兵」は `remainingForStars`。
- 枠とボタンの位置・大きさは、横長と縦長の両方で実際に置いた画面をユーザーに見せてから確定する（色・文字・枠の形は、いまあるボタンと同じ部品を使う）。**engine と測定（§7.9 の R13）が終わるまで、client の実装には入らない。**
