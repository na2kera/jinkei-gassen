## 2. いちばん大事な分け方

**engine が計算するのは「部隊」であって「兵」ではない。**

- engine が持つのは、1軍あたり最大16部隊ぶんの、位置・向き・兵数・士気・状態だけ。
- 部隊の中に並ぶ小さな兵は、client が兵数から描き起こす飾りで、engine は関知しない。
- 戦闘を映す側（client）は、engine の状態を直接読まず、`BattleSource`（§5.2）から届く「場面」だけを描く。1人用と対戦で同じ描画が使え、あとから斜め視点も足せる。

## 3. engine

### 3.1 原則

- **再現できる**。同じ初期状態・同じ種・同じ入力からは、同じ結果が出る。`Math.random`・`Date.now`・時計・通信に触れない。乱数は状態の中に持つ（32ビットの種から進める）。
- **時間は刻みで進む**。1刻み = 0.1秒（`DT = 0.1`）。engine は実時間を知らない。呼ぶ側が `step` を呼んだ回数だけ進む。毎秒いくつ、と書いた数字は、刻みごとに `DT` をかけて使う。
- **状態は JSON にそのまま保存できる形**。`Map`・`Set`・クラスのインスタンス・`undefined` の値を持たない。
- **例外を投げない**。不正な入力はエラーの結果として返す。利用者の入力が届く口（`createBattle`、`validateArmy`、`canOrder`、`canOrderView`、`applyTemplate`、`step` に渡す号令）は、どんな値を渡されても例外を投げない。`step` に渡す号令のうち不正なものは、無視して状態を変えない。
- **`step` に渡す状態は調べない**。状態は「`createBattle` が作り、`step` だけが書き換え、JSON にして戻しただけのもの」を前提にする。サーバーは、利用者から状態を受け取らない。
- **入力の量に上限を置く**。配置の数は、中身を見る前に上限で調べる。1回の `step` で見る号令は先頭の8件まで。予定された号令は32件まで。
- `step` は渡された状態を書き換える（毎刻みの複製を避けるため）。複製が要る側は自分で複製する。
- **判断は、刻みの初めの状態だけを見て行う**。どの部隊も、その刻みの初めの全部隊の位置・向き・状態を見て、狙い・動き・攻撃を決める。動きもダメージも士気も、全部隊ぶんを計算してから同時に適用する。処理する順番（id の順）で結果が変わらないようにする。
- 同点のときは、id の小さいほうを選ぶ。

**刻みの数え方**

- `state.tick` は、終わった `step` の回数。開戦時は 0。
- `step` は「刻み t = `state.tick`」を処理し、最後に `state.tick` を 1 増やす。
- 号令の期限は `untilTick` で持ち、`state.tick < untilTick` の間だけ有効。刻み t にかかった10秒の号令は `untilTick = t + 100` で、ちょうど100刻みのあいだ効く。
- 予定された号令（`scriptedOrders`）の `tick = t` は、`state.tick === t` の `step` の初めに出る。`tick = 0` は最初の `step` で出る。
- `step` の終わりに `state.tick === maxTicks` になり、決着していなければ時間切れ。標準の 1800 なら、ちょうど 1800 回の `step` で終わる。

**初期状態**

- id は、陣営0の配置を配列の順に 0 から、続けて陣営1の配置を配列の順に振る。
- 士気は 100。向きは自陣営の「前」。兵数は兵種の最大値。小数のまま持つ（映す側が切り上げて表示する）。
- 状態は `active`。狙いはなし。号令はなし。

### 3.2 座標と戦場

- 単位はマス。戦場は横 `width` × 縦 `height`。標準は 12 × 16（自軍の配置エリア6 + 中間地帯4 + 敵軍の配置エリア6）。
- 陣営は `0` と `1`。陣営0の配置エリアは下側（y が 10〜16）、陣営1は上側（y が 0〜6）。陣営0の「前」は y が減る向き、陣営1は増える向き。
- 部隊の位置はマスの中心（列 + 0.5、行 + 0.5）から始まり、戦闘中は連続した値で動く。
- 部隊の中心は、戦場の端から 0.45 より内側に保つ（敗走中を除く）。
- 地形はマスごとに持つ（§3.8）。段階1〜3はすべて平地だが、型と受け渡しは最初から入れておく。
- 翼は、配置した列で決まる：自分から見て左の3分の1が左翼、右の3分の1が右翼、あいだが中央。陣営1は向きが逆なので、列の大きいほうが左翼になる。戦闘中に動いても、翼は変わらない。

### 3.3 型

```ts
type Side = 0 | 1;
type Kind = 'infantry' | 'shield' | 'cavalry' | 'archer' | 'hq' | 'gate';   // gate は段階4（§3.8）
type Stance = 'advance' | 'hold' | 'flank' | 'hunt';               // 前進・守備・迂回・本陣狙い
type OrderKind = 'charge' | 'brace' | 'retreat';                   // 突撃・堅守・後退
type OrderTarget = 'all' | 'left' | 'center' | 'right';
type Terrain = 'plain' | 'hill' | 'forest' | 'river' | 'fence' | 'wall';

interface Placement { kind: Kind; col: number; row: number; stance: Stance }

interface Field {
  width: number; height: number;
  terrain: Terrain[];                       // 行優先。長さは width × height
  zones: [Zone, Zone];                      // 陣営ごとの配置エリア（マスの矩形）
}

interface BattleSetup {
  field: Field;
  armies: [Placement[], Placement[]];       // 戦場の座標で書く
  seed: number;
  maxTicks: number;                         // 標準は 1800（3分）
  timeout: 'compare' | 'side0_wins' | 'side0_loses';
  scriptedOrders?: { tick: number; side: Side; target: OrderTarget; kind: OrderKind }[];  // ステージの敵の号令
  requireHq?: boolean;                      // 既定は true。false は部分的な戦いのテスト用（下記）
}

interface Unit {
  id: number; side: Side; kind: Kind; wing: 'left' | 'center' | 'right';
  x: number; y: number; fx: number; fy: number;     // 位置と、向きの単位ベクトル
  men: number; maxMen: number; morale: number;      // 士気は 0〜100
  stance: Stance; home: { x: number; y: number };
  status: 'active' | 'routing' | 'gone';
  goneReason: null | 'routed' | 'destroyed';
  target: number | null;                            // 攻撃し、向く相手（§3.6.1）
  order: null | { kind: OrderKind; untilTick: number };
  stats: { dealt: number; taken: number; flankDealt: number; routsCaused: number };
  // ほかに、迂回の進み具合・騎兵の助走距離・最後に撃たれた刻み・敗走を始めた刻みを持つ
}

interface BattleState {
  tick: number; rng: number; field: Field; units: Unit[];
  ordersUsed: [number, number];
  maxTicks: number; timeout: BattleSetup['timeout'];
  outcome: null | { winner: Side | 'draw'; reason: 'hq' | 'wipeout' | 'timeout' | 'gate'; tick: number };
  // ほかに、開戦時の兵数の合計、最初に消えた部隊の記録、予定された号令、
  // 前の刻みに敗走・全滅した部隊の一覧（次の刻みの士気の計算に使う）
}
```

- `requireHq: false` のとき、本陣のない軍を認める。本陣のない軍には「本陣を討たれた」の負けはなく、全部隊が消えたら負け。合格条件の小さな場面（§3.9）のためのもので、画面からは使わない。
- 状態はただの JSON なので、テストは `createBattle` のあとで部隊の値を書き換えて場面を作ってよい。

### 3.4 公開する関数

```ts
createBattle(setup: BattleSetup): Result<BattleState>      // 配置を検査してから作る
step(state: BattleState, orders: OrderInput[]): BattleEvent[]   // 1刻み進める。決着後は何もしない
canOrder(state, side, target, kind): Result<true>          // §3.6.5 の受付の条件
viewFor(state: BattleState, viewer: Side | 'both'): BattleView  // 映す側に渡す場面
summarize(state: BattleState): BattleSummary               // 振り返り用

validateArmy(placements, zone, limits): ArmyError[]        // マスの重なり・エリア外・本陣の数・予算・部隊数
armyCost(placements): number
defaultStance(kind): Stance
wingOf(col, field, side): 'left' | 'center' | 'right'

listTemplates(): TemplateInfo[]                            // ひな形（§3.7）
applyTemplate(id, roster, zone, side): Placement[]
recognizeFormation(placements, zone, side): { id: string; name: string } | null   // 段階2

STAGES: Stage[]                                            // ステージのデータ（§3.10）。段階2
PVP_RULES: { budget, costs, maxUnits }                     // 対戦の予算。段階3
```

**映す側に渡す型は、渡してよい項目だけを書き出して作る**（状態をそのまま複製して項目を消す作りにしない）。

```ts
interface UnitView {
  id: number; side: Side; kind: Kind; wing: 'left' | 'center' | 'right';
  x: number; y: number; fx: number; fy: number;
  men: number; maxMen: number; morale: number;
  status: 'active' | 'routing' | 'gone';
  order: OrderKind | null;
  attacking: number | null;        // この刻みに実際に攻撃した相手（近接でも弓でも）。攻撃していなければ null
  stance?: Stance;                 // 自軍の部隊だけ。viewer が 'both' なら全部隊
}
interface BattleView {
  tick: number; maxTicks: number; units: UnitView[];
  ordersLeft: [number, number];
  outcome: BattleState['outcome'];
}
type BattleEvent =
  | { type: 'order'; tick: number; side: Side; target: OrderTarget; kind: OrderKind }
  | { type: 'rout'; tick: number; unit: number }
  | { type: 'destroyed'; tick: number; unit: number }
  | { type: 'impact'; tick: number; attacker: number; defender: number; facing: 'front' | 'side' | 'rear' }  // 騎兵の突入
  | { type: 'end'; tick: number; winner: Side | 'draw'; reason: string };
interface BattleSummary {
  winner: Side | 'draw'; reason: string; seconds: number;
  remaining: [number, number];          // 残った兵の割合。敗走・全滅した部隊は0と数える
  units: { id: number; side: Side; kind: Kind; menLeft: number; dealt: number; routsCaused: number; fate: 'alive' | 'routed' | 'destroyed' }[];
  firstBroken: [number | null, number | null];   // 陣営ごとに、最初に消えた部隊
}
```

- `attacking` は、戦場を見ていれば分かること（誰が誰を打っているか、誰に矢が飛んでいるか）なので、両軍ぶんを渡す。向かっているだけで、まだ攻撃していない相手（狙い）は渡さない。
- 相手の部隊の方針・狙い・持ち場・迂回の進み具合・助走は、`BattleView` に含めない。出来事にも含めない。テストで、相手ぶんの `UnitView` に上の項目以外の鍵がないことを確かめる。
- 出来事は、1部隊につき敗走1回・全滅1回まで。

### 3.5 部隊の数字（初期値）

| 兵種 | 兵数 | 速さ（マス/秒） | 近接の攻撃（毎秒） | 回転（度/秒） | 特徴 |
|---|---|---|---|---|---|
| 歩兵 | 100 | 1.0 | 3.0 | 180 | なし |
| 盾兵 | 100 | 0.7 | 2.2 | 120 | 正面からの近接は 0.45 倍、弓は 0.4 倍。正面からの騎兵の突入を止める |
| 騎兵 | 60 | 2.2 | 3.6 | 240 | 助走をつけて当たると突入（§3.6.2） |
| 弓兵 | 80 | 0.9 | 1.2 | 180 | 4.5 マス先まで撃てる（毎秒 2.4）。近接で受ける損害は 1.3 倍 |
| 本陣 | 80 | 0.6 | 2.6 | 120 | 受ける損害は 0.7 倍。3.5 マス以内の味方の士気を支える |

- 部隊どうしの中心は、味方でも敵でも 0.9 より近づかない（§3.6④）。
- 近接が届く距離（近接の距離）は、中心どうしで 1.05。

### 3.6 1刻みの中身

順番は次のとおり。①〜③と⑤〜⑦の判断は、刻みの初めの状態を見て行う。

1. **号令を受け付ける**（§3.6.5）。予定された号令も、ここで出す。
2. **切れた号令を外す**（`state.tick >= untilTick`）。外すときの後始末は §3.6.5。
3. **狙いと、動く向きを決める**（§3.6.1）。
4. **動く**（下記）。
5. **向きを変える**。向きたい方向へ、回転の上限つきで回る。向きたい方向は、狙いがあれば狙いのほう、なければ動く向き、どちらもなければ自陣営の「前」。後退の号令中は、狙いにかかわらず動く向き（後ろ）。
6. **戦う**（§3.6.2）。
7. **兵数と士気をまとめて動かす**（§3.6.3）。兵数が0以下の部隊は全滅（`gone`）、士気が0以下の部隊は敗走（`routing`）にする。両方なら全滅。
8. **決着を調べる**（§3.6.4）。
9. `state.tick` を 1 増やす。時間切れを調べる。

**状態ごとの扱い**

| | `active` | `routing` | `gone` |
|---|---|---|---|
| 動く | 方針と号令に従う | 自陣の奥へまっすぐ、速さ 1.3 倍で逃げる。敗走した次の刻みから | 動かない |
| 攻撃する | する | しない | しない |
| 攻撃される | される | いま狙われている相手からだけ、される（下記） | されない |
| ほかの部隊とぶつかる | ぶつかる | ぶつからない（すり抜ける） | ぶつからない |
| 味方の支え・本陣の支え・囲みに数える | 数える | 数えない | 数えない |
| 号令がかかる | かかる | かからない | かからない |

- 敗走中の部隊は、戦場の端を越えるか、敗走から5秒（50刻み）たつと `gone`（理由は `routed`）になる。立て直しはしない。
- 敗走中の部隊が追い打ちで全滅しても、まわりの士気への影響は、敗走したときの1回だけ（全滅のぶんは足さない）。
- 敗走した部隊を狙っていた部隊は、その部隊が近接の距離（弓兵なら撃てる距離）にいる間だけ、攻撃を続けてよい。新しく狙う相手に、敗走中の部隊は選ばない。

**④ 動き方**

1. 各部隊が、刻みの初めの位置から、動きたい分（向き × 速さ × `DT`）を決める。戦う部隊と、守備・堅守で持ち場にいる部隊は、動かない。この「動かない部隊」を、この刻みの**錨**と呼ぶ。
2. 動きたい先が、ほかの `active` な部隊（味方でも敵でも。刻みの初めの位置で見る）の 0.9 以内に入るなら、0.9 の手前で止まり、残りの分は、相手のまわりを回る向き（接線）に半分の速さで進む。回る向きは、動きたい向きに近いほう。真正面なら、狙いが左右どちらにあるかで決め、それも同じなら左。
3. 全部隊を同時に動かす。
4. 重なりをほどく。2回くり返す：中心が 0.9 より近い `active` な2部隊を、結ぶ線に沿って、重なりの半分ずつ離す。片方が錨なら、もう片方だけを重なりの分ぜんぶ動かす。両方が錨なら動かさない。位置がまったく同じなら、id の小さいほうを左、大きいほうを右へ離す。くり返しの中の計算は、その回の初めの位置で行い、同時に適用する。
5. 戦場の内側（端から 0.45）に収める。

- この決まりで、戦っている味方の後ろの部隊は、通り抜けずに脇へ回り込む。列の端からあふれた部隊が敵の側面に回り、敵の列に穴が空けば後ろの部隊がそこへ入る。包囲と突破は、ここから生まれる。

#### 3.6.1 狙いと方針

部隊は、狙い（`target`）を1つだけ持つ。**狙いは、攻撃する相手であり、向く相手でもある。**

**近接の距離に敵がいるとき**（どの方針でも同じ。ただし下の「戦わない場合」を除く）

- いまの狙いが近接の距離にいれば、狙いを変えない。後ろや横から別の敵が当たっても、向きは変わらない。これが、側面・背面を突かれる仕組みになる。
- いまの狙いが近接の距離にいなければ、近接の距離にいる敵のうち、いまの向きにいちばん近い方向にいる敵を狙う。同じなら近いほう。
- この部隊は戦う（動かない）。

**近接の距離に敵がいないとき**

| 方針 | 狙いと動き |
|---|---|
| 前進 | `距離 + 横のずれ（x の差の絶対値）` がいちばん小さい敵を狙い、そちらへ進む。いまの狙いが残っている間は、ほかの敵の値が 1.0 以上小さくならない限り、狙いを変えない |
| 守備 | 持ち場（`home`）にいる。持ち場から 0.1 より離れていたら戻る。4マス以内に敵がいれば、いちばん近い敵を狙う（向くだけで、近づかない） |
| 迂回 | ①自分に近いほうの端の列（端から 0.5）へ横に出る。②端に沿って、開戦時の敵軍の重心の行より 1.5 マス奥（敵陣側）まで進む。戦場に収まらなければ収まるところまで。③そこから、本陣以外でいちばん近い敵を狙って進む（本陣しか残っていなければ本陣）。①②の間は狙いを持たない。途中で敵と戦って、その敵が消えたら、続きから再開する |
| 本陣狙い | 敵の本陣を狙い、まっすぐそちらへ進む。途中の敵にぶつかったら、④の決まりで相手のまわりを回り、敵の列に沿って滑って、端か穴から抜ける。敵の本陣がなければ、前進と同じ |

- 迂回で、左右どちらの端も同じ近さのときは、開戦時にその側にいる敵の部隊が少ないほうへ出る。それも同じなら左。
- 本陣狙いの部隊は、**本陣以外の敵とは戦わない**（正面にいても戦わず、すれ違う敵から打たれながら進む）。戦うのは、敵の本陣が近接の距離に入ったときだけ。
  - 滑る向き（左右）は、何かにぶつかり続けている間は変えない。何にもぶつからずに動けた刻みで、決め直す。
  - 詰まったとき：2秒前の位置から 0.3 マスも進めていなければ、近接の距離にいるいちばん近い敵と戦う。その敵が消えるか離れたら、また本陣へ向かう。
- 迂回の①②の部隊は、近接の距離に敵がいても、その敵が進む向きの正面（±50°以内）にいなければ戦わずに進み続ける。正面にいれば、ふつうに戦う。
- 狙いが消えたら（敗走して攻撃を続けられなくなった場合を含む）、その刻みから上の決まりで選び直す。

**兵種ごとの違い**

- 弓兵は、近接の距離に敵がいなければ撃つ。撃てる距離（4.5）にいる `active` な敵のうち、いちばん近い敵を狙う。前進・迂回の③・本陣狙いの弓兵は、撃てる相手がいる間は止まって撃つ。守備の弓兵は持ち場から撃つ。味方には当たらず、味方ごしに撃てる。
- 弓兵は、近接の距離（1.05）に敵がいる間は撃てず、近接で戦う。
- 本陣が選べる方針は、守備と前進だけ。
- 初期設定：歩兵は前進、盾兵は守備、騎兵は迂回、弓兵は前進、本陣は守備。

**優先する順番**：敗走 → 号令 → 兵種ごとの違い → 方針。号令中の動きは §3.6.5。

#### 3.6.2 損害

損害は、次の3つの掛け算で出す。部隊は、狙いにだけ攻撃する（1刻みに1相手）。

```
損害 = もとの値 × 攻める側の倍率 × 受ける側の倍率
```

| | 近接（毎秒） | 弓（毎秒） | 騎兵の突入（1回） |
|---|---|---|---|
| もとの値 | 兵種の攻撃 | 2.4 | 12 |
| × √(攻める側の兵数 ÷ 最大兵数) | かける | かける | かける |
| × ばらつき（0.9〜1.1 の乱数） | かける | かける | かけない |
| 攻める側：突撃の号令中 1.3 | かける | かける | かける |
| 攻める側：相性 | 騎兵→弓兵 1.5、歩兵→弓兵 1.2 | なし | なし |
| 受ける側：向き | 正面 1.0、側面 1.5、背面 2.0 | かけない | 正面 1.0、側面 1.5、背面 2.0 |
| 受ける側：盾兵の正面 | 向きの代わりに 0.45 | 0.4 | 向きの代わりに 0.2 |
| 受ける側：本陣 0.7、弓兵（近接と突入）1.3 | かける | 本陣だけ | かける |
| 受ける側：突撃中 1.2、堅守中 0.7 | かける | かける | かける |
| 地形（§3.8） | かける | かける | かける |

- **向き**は、受ける側の向きと、受ける側から攻める側への方向のなす角で決める：50°以内が正面、120°を超えると背面、あいだが側面。
- 正面の角度は 52° より小さくしておく。正面の相手と組み合っている部隊に、3部隊目が近接の距離まで寄ると、部隊どうしの間隔（0.9）のせいで、角度は必ず 52° ほどより外になる。これを側面と数えないと、列の端から回り込んでも側面にならず、包囲が生まれない。
- **騎兵の突入**：騎兵が、近接の距離に敵がいない状態で続けて 2.0 マス以上動いたあと（止まった刻みで、助走は 0 に戻る）、狙いが近接の距離に入った刻みに、1回だけ起きる。上の損害に加えて、士気への衝撃（正面 −10、側面 −18、背面 −25。堅守中は 0.6 倍）を与える。盾兵の正面に当たった場合は、士気への衝撃はなく、騎兵のほうが兵数 8 と士気 8 を失う。森の中の相手・柵の中の相手には起きない。起きたら助走は 0 に戻る。
- 損害は、残っている兵数までしか入らない。`stats.dealt` と `stats.taken` には、実際に入った分を足す。側面・背面から与えた近接と突入の損害は `stats.flankDealt` にも足す。

#### 3.6.3 士気

1刻みの士気の増減を、部隊ごとにすべて足し合わせてから、1回で適用する。そのあと 0〜100 に収めて、敗走を判定する。

**損害による減り**（損害1件ごとに計算して足す）

```
士気の減り = (その損害で失った兵数 ÷ 最大兵数) × 120 × 向き × 支え
```

- 向き：近接と突入は、正面 1.0、側面 1.6、背面 2.4。弓は向きにかかわらず 0.6。
- 支え：1.6 マス以内の `active` な味方（自分を除く。本陣も1部隊として数える）1部隊ごとに 0.15 軽くなる（3部隊まで。つまり最小 0.55）。本陣が 3.5 マス以内なら、さらに 0.7 倍（本陣自身にはかからない）。堅守中は、さらに 0.6 倍。

**そのほかの増減**

| 条件 | 増減 |
|---|---|
| 囲まれている：近接で攻めてくる敵が2部隊以上いて、そのうち2部隊の方向が 100°以上開いている | 毎秒 −2 |
| 騎兵の突入を受けた | §3.6.2 の衝撃 |
| 前の刻みに、2.0 マス以内の味方が敗走した | 1部隊につき −12 |
| 前の刻みに、2.0 マス以内の味方が全滅した | 1部隊につき −6 |
| 前の刻みに、自分が狙っていた敵が敗走・全滅した | +8 |
| 前の刻みに、2.5 マス以内の敵が敗走・全滅した（上を除く） | 1部隊につき +3 |
| 2.0 マス以内に敵がおらず、この2秒のあいだ損害を受けていない | 毎秒 +1.5 |
| 本陣が 3.5 マス以内にいる（本陣自身を除く） | 毎秒 +1 |
| 号令がかかった刻み | 突撃 +5、堅守 +10 |

- **敗走・全滅の影響は、次の刻みに伝わる**。刻み t に敗走した部隊のまわりの味方は、刻み t+1 の計算で −12 を受ける。それで崩れた部隊の影響は、刻み t+2 に伝わる。崩れは、0.1 秒に1部隊ぶんずつ、波のように広がる。
- 「自分が狙っていた」は、その敵が消えた刻みの初めに、その敵を狙いにしていた部隊すべて。`stats.routsCaused` も、その全部隊に 1 ずつ足す。

#### 3.6.4 決着

刻みの終わりに、陣営ごとに「負けの条件」を調べる。

- **本陣**：本陣が全滅・敗走した（`routing` になった刻みで成立。消えるのを待たない）。
- **壊滅**：本陣以外の部隊が、すべて全滅・敗走した（最後の1部隊が `routing` か `gone` になった刻みで成立）。

| 条件を満たした陣営 | 結果 |
|---|---|
| 片方だけ | もう片方の勝ち。理由は、本陣の条件を満たしていれば `hq`、そうでなければ `wipeout` |
| 両方 | 引き分け。理由は、どちらかが本陣の条件を満たしていれば `hq`、そうでなければ `wipeout` |
| どちらもなし | 続行。`state.tick` を増やしたあと `maxTicks` に達していれば時間切れ（`timeout`） |

- 同じ刻みに、決着と時間切れが重なったら、決着を優先する。
- 時間切れの `compare`：残った兵の割合（`active` な部隊の兵数の合計 ÷ 開戦時の兵数の合計。本陣を含む）を、百分率に四捨五入して比べる。大きいほうの勝ち。同じなら引き分け。
- `side0_wins`・`side0_loses` はステージ用。

#### 3.6.5 号令

**受け付けの条件**（1つでも外れたら受け付けず、回数も減らず、状態も変わらない）

- 決着していない。
- その陣営の使った回数が 3 未満。
- 対象の翼（`all` なら全軍）に、その号令がかかる `active` な部隊が1つ以上いる。突撃は本陣にかからないので、本陣しかいない翼への突撃は受け付けない。

同じ `step` に複数の号令が来たら、配列の順に1つずつ調べる。

| 号令 | 続く長さ | 号令中の動き |
|---|---|---|
| 突撃 | 10秒 | 方針が前進になる（弓兵は、撃てる相手がいれば止まって撃つ）。攻撃 1.3 倍、受ける損害 1.2 倍、速さ 1.25 倍。本陣にはかからない |
| 堅守 | 10秒 | その場で止まる（持ち場には戻らない）。近接の距離の敵とは戦い、弓兵は撃つ。受ける損害 0.7 倍、士気の減り 0.6 倍 |
| 後退 | 6秒 | 自陣の奥へまっすぐ下がる。**戦わず、撃たない**。近接の距離に敵がいても動く。向きは、回転の上限つきで後ろへ回る（背中を見せる）。配置エリアのいちばん奥の2行に入ったら止まり、そこからは堅守と同じ動き（倍率はなし）で残りの時間を過ごす |

- 号令がかかった部隊は、それまでの号令が終わり、新しい号令に入れ替わる。同じ種類の号令をもう一度かけてもよい（長さが延び、士気の上乗せももう一度入る。回数は減る）。
- **号令が終わるときの後始末**（期限が来たとき、新しい号令に入れ替わるとき、どちらでも）：方針が守備の部隊は、その時点の位置を新しい持ち場にする。迂回の部隊は、進み具合をそのまま引き継ぐ。
- 号令が終わったら、元の方針に戻る。

### 3.7 ひな形と陣形名

ひな形は、手持ちの部隊（兵種ごとの数）と配置エリアを受け取って、配置と方針を返す関数。部隊の数が 6〜16 のどれでも、エリアに収まり、重ならず、全部隊を使い切ること。同じ入力からは、いつも同じ配置を返す。

**ひな形は段階1で作る**（合格条件の総当たりに使うため）。陣形名の判定は段階2で作る。

| id | 名前 | 形（自軍から見て。上が敵） | 兵種の割り当てと方針 |
|---|---|---|---|
| `line` | 横陣 | 横一列に2段 | 前列に盾兵と歩兵（前進）、後列に弓兵、両端に騎兵（迂回） |
| `crane` | 鶴翼 | V字。両翼が前に張り出し、中央が下がる | 中央に盾兵（守備）と弓兵、両翼に歩兵（前進）、翼の先に騎兵（迂回） |
| `scale` | 魚鱗 | 先がとがった三角形で、中央が厚い | 先に歩兵（前進）、中に盾兵（前進）、後ろに弓兵、騎兵は後ろの両脇（前進） |
| `arrow` | 鋒矢 | 矢印。細く深い縦の列で、先が矢じり | 矢じりに騎兵（本陣狙い）と歩兵（前進）、軸に盾兵（前進）、弓兵は後ろ |
| `ring` | 方円 | 本陣を囲む輪 | 外側に盾兵と歩兵（守備）、内側に弓兵（守備）、騎兵は輪の中（守備） |
| `crescent` | 偃月 | 弓なり。中央が前に出て、両翼が下がる | 中央の前に歩兵と騎兵（前進）、両翼に盾兵（守備）、弓兵は後ろ |
| `echelon` | 雁行 | 斜めの段々 | 前の段から歩兵（前進）、盾兵（前進）、弓兵。騎兵は前に出た側の端（迂回） |

- 本陣は、どのひな形でも後ろの中央（方円は輪の中心）。
- 兵種が足りない・余るときは、役割の近い兵種で埋める（盾兵 ↔ 歩兵、騎兵 → 歩兵、弓兵 → 歩兵の後ろ）。
- **陣形名の判定**：本陣を除いた配置のマスの集合 P と、同じ手持ちで作った各ひな形のマスの集合 T を比べる。横に ±2、縦に ±1 ずらした中で、`|P∩T| ÷ max(|P|, |T|)` がいちばん大きい値を、そのひな形の点とする。点が 0.75 以上で、2番目との差が 0.05 以上あるひな形の名前を返す。兵種と方針は見ない。雁行は左右どちら向きも同じ名前にする。

### 3.8 地形（段階4）

部隊の地形は、中心があるマスで決める。数字は初期値で、§3.9 の条件と下の「地形の条件」を満たすように調整してよい。ただし、平地だけの戦いの結果は、地形を入れる前と1刻みも変わらないこと（§3.9 の A1〜A15 と第1章の面のテストが、数字を変えずにそのまま通ること）。

| 地形 | 効果（初期値） |
|---|---|
| 丘 | 高低は「丘のマスにいるか、いないか」の2段だけ。丘の上の部隊が、丘の外の相手に近接で与える損害 1.2 倍。丘の外の部隊が、丘の上の相手に近接で与える損害 0.85 倍。丘の上の弓兵は、届く距離 +1.5。丘のマスにいる間の速さ 0.85 倍 |
| 森 | 森のマスにいる間の速さ 0.8 倍（騎兵は 0.5 倍）。攻める側か受ける側のどちらかが森にいれば、騎兵の突入は起きない。森の中の部隊が弓から受ける損害 0.5 倍 |
| 川 | 川のマスにいる間の速さ 0.5 倍。川の中の部隊は、近接の攻撃 0.7 倍、受ける損害（近接・弓・突入）1.3 倍。川の中の騎兵は突入できない |
| 柵 | 柵のマスにいる部隊は、**正面から**受ける近接の損害 0.55 倍、弓の損害 0.5 倍、正面からの騎兵の突入なし。側面・背面からは効果なし。攻める側も柵のマスにいるときは、効果なし（中に入られたら、柵は役に立たない）。柵のマスにいる間の速さ 0.4 倍 |
| 城壁（岩壁） | どの部隊も通れない。弓は越える（城壁の上から撃ち合うことを、こう表す）。谷の両側の岩壁にも、この地形を使う |

- 柵に「どちらの陣営のもの」という区別は持たせない。柵のマスに立って、敵に正面を向けている部隊が守られる。これで「守る側が正面から崩されにくい」になる。
- 倍率の掛け方は §3.6.2 の表の「地形」の行に入れる。盾兵の正面と柵の正面は、両方かける。

**通り道**（城壁があるとき）

- 行き先（狙い、持ち場、迂回の通過点、敵の本陣）へ向かうとき、まっすぐ進む線が城壁のマスを横切るなら、マス目の上の最短の道（上下左右と斜め。城壁は通れない。斜めは、両隣のどちらかが城壁なら通れない）をたどり、道の上で「いまの位置からまっすぐ見通せる、いちばん先のマス」へ向かう。
- 道の計算は、城壁のある戦場でだけ行う。城壁のない戦場では、今までと同じ動きをする。
- 前進の狙いを選ぶときの「距離」は、城壁のある戦場では、道の長さを使う。
- 迂回で出る「端の列」は、その行で城壁でない、いちばん外側の列とする。
- 門のマスは、道の計算では通れるものとして扱う（門が立っていても）。

**門**（`kind: 'gate'`）

- 守る側（面のデータでは陣営1）の部隊として置く。動かない、攻撃しない、向きは変えない。士気を持たず、敗走しない。耐久（`men`）は 150。
- 近接の損害は、向きの倍率なしで、そのまま受ける。弓の損害は 0.1 倍。騎兵の突入は受けない。
- ほかの部隊と同じように場所を取る（中心どうし 0.9）。門が立っている間、そのマスは通れない。全滅すると消えて、通れるようになる。
- 号令はかからない。味方の支え・囲み・本陣の支えには数えない。まわりの士気にも影響しない（消えても、味方は動揺しない）。
- 「本陣以外の部隊がすべて消えた」の判定と、残った兵の割合（時間切れの比べ方、星）には、門を数えない。
- 狙われ方：前進・迂回③・詰まった本陣狙いの部隊は、門もふつうの敵として狙える。ただし、選んだ狙いへの道が、立っている敵の門のマスを通るなら、狙いを門に替える（門を破らないと先へ進めないため）。弓兵は、ほかに撃てる敵がいれば門を撃たない。
- 門は、1つの戦場に1つまで。

**決着**（§3.6.4 に足す）

- 面の `win` が `gate` のとき、門が全滅した刻みに、陣営1は「負けの条件」を満たす（理由は `gate`）。本陣・壊滅の条件と同じ扱いで、同じ刻みに陣営0も負けの条件を満たしていたら引き分け。理由の優先は、`gate`、`hq`、`wipeout` の順。
- `win` が `gate` の面でも、本陣を討つ・壊滅させるの決着はふつうに起きる。時間切れは負け。
- `win` が `gate` でない面に門を置いた場合、門が破れても決着しない（通れるようになるだけ）。

**面のデータに足すもの**（§3.10）

- `seconds?: number`：面の長さ。省略すると 180 秒。「時間を稼ぐ」面を短くするために使う。
- 敵の配置エリア：面ごとに `field.zones[1]` を広げてよい（中間地帯まで含めるなど）。挟み撃ちの面では、敵を自軍の配置エリアの真横に置く。面のデータは作る側が書くものなので、敵の配置は「戦場の中で、城壁でなく、重ならない」だけを検査する。
- 自軍の配置エリアに、城壁のマスが入っていてもよい。そのマスには置けない（配置の検査で落とす。画面でも置けないことが分かるようにする）。

**地形の条件**（合格条件に足す。場面は §3.9 の共通の決まりに従う）

| # | 条件 |
|---|---|
| T1 | 丘：歩兵3（守備、丘の上）対 歩兵3（前進、丘の外から）。丘の上の側の得点率が、同じ配置を平地に置いた場合より 0.2 以上高い |
| T2 | 森：騎兵2が、森の中の歩兵1（守備）に側面から突っ込む。平地なら歩兵が15秒以内に消える種が8割以上。森の中なら、15秒後に歩兵が残っている種が8割以上 |

## 4. server（段階3）

### 4.1 作り

- Worker が `/api/*` を受け、それ以外は client の静的ファイルを返す。
- 部屋1つを Durable Object 1つが受け持つ（SQLite バックエンド）。部屋のコード（4桁の数字）から `idFromName` で引く。
- WebSocket は Hibernation API（`ctx.acceptWebSocket`）で受ける。部屋が動いていない間は、Durable Object が眠れる。
- `compatibility_date` は `2026-11-01`。
- Origin の確認と、メッセージの大きさ・頻度の上限は、超富豪の server と同じ考え方で入れる。

### 4.2 通信の方式

**サーバーが engine を刻み、席ごとに見える場面を送る。** 各自の端末で同じ計算を並行して走らせる方式は採らない。理由は2つ：相手の方針を端末に送らずに済むこと、戦闘の途中で戻った人にその時点の場面を渡せば済むこと。

**戦闘の刻み方**

- 戦闘中は `setInterval`（100ms）で刻む。戦闘の時計は `clockBase`（刻み0にあたる実時刻）で持ち、呼ばれるたびに `(今 − clockBase) ÷ 100ms` と `state.tick` の差だけ `step` を呼ぶ。1回の呼び出しで最大5刻み。
- それでも 0.5 秒より大きく遅れているときは、追いかけず、`clockBase` を今に合わせ直す（その分、戦闘が止まっていたことにする）。小さな遅れは吸収し、大きな中断は戦闘の一時停止として扱う。
- 号令は、届いた次の `step` に渡す。
- 場面（`snap`）は2刻みごと（毎秒5回）に、席ごとに `viewFor` を通して送る。**出来事は、前の `snap` のあとに起きた分をためて、まとめて送る**（奇数の刻みの出来事を落とさない）。決着した刻みは、2刻みを待たずにすぐ送る。
- 決着したら `setInterval` を止める（止めないと Durable Object が眠れない）。

**保存と再開**

- Durable Object のメモリは、眠ったり作り直されたりすると消える。**部屋の状態は、変わるたびに保存領域へ書く**（下の `RoomState`）。コンストラクタで読み戻し、つながっている WebSocket を `ctx.getWebSockets()` と添付データ（席の番号と接続の番号）から組み立て直す。
- 戦闘の状態（engine の `BattleState`）は、別の鍵で、20刻みごと（2秒ごと）・号令を受け付けた `step` の直後・決着時に書く。号令を使った回数が巻き戻らないようにするため。保存が要る刻みでは、保存してから場面を送る（相手に見せた号令が、復帰後に巻き戻らないようにする）。
- 書き込みの数を抑える：無料プランには、書き込みが1日10万行までという枠もある。最長の1戦（3分）で約140行で、1日に約700戦ぶん。見張りの時刻と「アラームを入れた時刻」は、保存せずメモリにだけ持つ。
- 号令が届いてから次の `step` までの間（最長 0.1 秒）に Durable Object が消えると、その号令は失われる。その場合、相手にも表示されておらず、回数も減っていないので、食い違いは起きない。
- 作り直されたあとの再開：保存した刻みから続ける。`clockBase` は「今 − 保存した刻み × 100ms」に合わせ直す。追いかけない。
- **見張りのアラーム**：戦闘中は、10秒先にアラームを入れ続ける（延ばすのは、戦闘の保存と同じ機会に、残りが半分を切ったときだけ）。アラームが鳴ったときに `setInterval` が動いていなければ（作り直された直後）、戦闘を再開する。誰もつながっていなくても、戦闘は最後まで進む。

**期限**

- 配置の制限時間、公開から開戦までの間、不在の判定、予約の期限、部屋の片付け、見張りは、アラーム（`setAlarm`）で扱う。期限は `RoomState` に時刻で持ち、いちばん近いものをアラームに入れる。
- アラームの候補は、段階で絞る（予約は予約中、配置の期限は配置中、公開は公開中、不在は結果の間、片付けは戦闘以外、見張りは戦闘中だけ）。次に入れる時刻が今以前になる場合は、入れずに記録を残す（過ぎた期限が残って、アラームが鳴り続けるのを防ぐ）。
- アラームは2回以上呼ばれることがある。アラームの処理は「今の時刻と、保存してある期限と、今の段階」だけを見て進め、**何回呼ばれても、段階の移り変わりと成績の加算が1回だけになる**ようにする（移る前に段階と戦闘の番号を確かめる）。

> Cloudflare の公式資料で確かめたこと（2026-11-16）：
> - `setInterval` が動いている間、Durable Object は眠らず、実行時間が課金の対象になる。無料プランの枠は1日 13,000 GB-秒で、128MB の Durable Object が1日に約28時間動ける計算になる。1戦は最長3分なので、友達どうしで遊ぶ量なら足りる。
> - `compatibility_date` が `2026-10-01` 以降なら、動いている `setInterval` が、接続のない間も Durable Object の追い出しを防ぐ（1つの操作につき最長15分）。
> - 眠るとメモリの中身は捨てられる。WebSocket ごとの添付データは残る。
> - アラームは少なくとも1回の実行が保証され、失敗すると再試行される。
> - 受け取る WebSocket のメッセージは、20通で1リクエストと数える。送るほうは数えない。

### 4.3 部屋の状態と流れ

```ts
interface RoomState {
  gen: number;                 // 部屋の世代。部屋を作るたびに乱数で決める
  phase: 'reserved' | 'waiting' | 'setup' | 'reveal' | 'battle' | 'result';   // 部屋がないことは、記録がないことで表す
  battleNo: number;            // この部屋で何戦目か
  seats: [Seat | null, Seat | null];
  score: [number, number, number];        // 陣営0の勝ち、陣営1の勝ち、引き分け
  map: string;                 // 戦場の id
  deadlines: { setup?: number; reveal?: number; reserve?: number; idle?: number; away?: number };
  rematch: [boolean, boolean];
  lastResult?: BattleSummary;
}
interface Seat {
  pid: string; name: string;
  conn: number | null;         // いま有効な接続の番号。切れていれば null
  goneSince: number | null;    // 切れた時刻
  ready: boolean;
  draft: Placement[] | null;       // 最後に届いた下書き
  lastValid: Placement[] | null;   // 最後に検査を通った下書き
}
```

```
empty → reserved（作った人の接続待ち）→ waiting（1人）→ setup（配置。120秒）→ reveal（公開。3秒）→ battle（最長180秒）→ result → setup …
```

- **部屋を作る**：`POST /api/rooms`（本文に `pid`）。Worker が4桁のコードを乱数で選び、その Durable Object に「作成」を頼む。Durable Object は、記録がないときだけ、`gen` を乱数で決めて `reserved` にし、作った人の `pid` を覚える（空きの確認と予約を、1回の処理で行う）。空いていなければ断り、Worker が別のコードで最大8回やり直す。それでもだめなら「混み合っています」を返す。予約は60秒で切れ、記録を消す。
- **入る**：`GET /api/rooms/:code/ws?pid=…&name=…`。
  - `reserved` で、`pid` が作った人のものなら、陣営0の席に着いて `waiting` へ。
  - 席にいる `pid` なら、その席に戻る。
  - 空いた席があれば、そこに着く。2人そろったら `setup` へ。
  - それ以外（部屋がない、満員）は断る。
- **1つの席に有効な接続は1つ**。同じ `pid` で新しくつなぐと、古い接続を閉じて入れ替える。古い接続の「切れた」という知らせは、接続の番号が今のものと違えば無視する。
- `pid` は、端末が作る128ビットの乱数（16進の文字列）。席に戻るための合言葉として扱い、相手には送らない。
- 部屋を作った人が陣営0、入った人が陣営1。どちらの画面でも自軍が下に見えるように、client が上下左右を返して描く。
- **`setup`**：戦場を選び（段階3は平原だけ）、期限を決める。client は、配置が変わるたびに下書きを送る（0.5秒に1回まで）。「完了」で確定し、確定中の下書きは受け付けない（取り消せば、また受け付ける）。2人とも確定するか、期限が来たら `reveal` へ。確定していない人は、最後に検査を通った下書きを使う。それもなければ、既定の編成（R15）を横陣で並べる。
- **`reveal`**：両軍の配置（方針を除く）を両者に送る。3秒後に `battle` へ。`battleNo` を増やす。
- **`battle`**：号令を受け付ける。切れている人の部隊はそのまま戦う。戻ってきた人には、`room` と、その時点の `snap` を送る。
- **`result`**：勝敗を成績に足し、`result` を送る。両者が「もう一戦」を押すと `setup` へ。
- **不在**：`result` の間、切れてから60秒以上たった席は空ける。`result` に入った時点ですでに60秒以上の席も、`result` の途中で60秒に達した席も同じ。席が空いたら、成績を消して `waiting` に戻し、残った人に「相手を待っています」と出す。2人ともいなければ、下の片付けに任せる。
- **片付け**：誰もつながっていない状態が10分続いたら、保存した内容とアラームをすべて消す（`deleteAll`）。何も残さない。
- **回数の上限**：送信元の IP ごとに、部屋の作成は1分に10回、入室の試みは1分に30回まで（Cloudflare の Rate Limiting の binding。超えたら 429）。4桁のコードの総当たりと、作成の連打を抑える。数え方はおおよそで、拠点ごと。
- **違反した接続は閉じる**：バイナリ、大きすぎるメッセージ（4096文字超）は、すぐ閉じる。頻度は、ためておける分（20通）を使い切ったあと、さらに20通届いたら閉じる。閉じた席は「切れた」になり、同じ `pid` で入り直せる。

### 4.4 メッセージ

型は `packages/server/src/protocol.ts` に置き、client が型だけを読み込む。

| 向き | 種類 | 中身 |
|---|---|---|
| S→C | `room` | 段階、`battleNo`、席（名前・接続中か・確定したか。`pid` は含めない）、成績、期限の時刻、自分の陣営、戦場、予算 |
| S→C | `reveal` | 両軍の配置（相手の方針なし）、開戦の時刻 |
| S→C | `snap` | `battleNo`、刻み、部隊の一覧（詰めた配列）、前の `snap` のあとの出来事、残りの号令 |
| S→C | `result` | `battleNo`、勝者、理由、振り返り、成績 |
| S→C | `error` | 理由（部屋がない、満員、配置が不正、号令が不正） |
| C→S | `draft` | 配置の下書き |
| C→S | `ready` / `unready` | 配置の確定と取り消し |
| C→S | `order` | `battleNo`、相手（翼）、号令の種類 |
| C→S | `rematch` | `battleNo` |

- **受け付ける段階**：`draft`・`ready`・`unready` は `setup` だけ。`order` は `battle` で、`battleNo` が今のものと同じときだけ。`rematch` は `result` で、`battleNo` が同じときだけ。それ以外は黙って捨てる（前の戦いから遅れて届いたメッセージが、今の戦いに効かないようにする）。
- 配置はサーバーが `validateArmy` で検査する（自分のエリア内、重なりなし、本陣1つ、予算内、部隊数の上限）。
- 対戦の配置は、どちらの席も「自分が下」の座標で送る。サーバーが、陣営1のぶんを上下左右に返して戦場の座標にする。場面を陣営1に送るときも、同じように返す（左翼・右翼も、自分から見た向きになる）。
- 相手に送るものに、相手の方針・狙い・下書き・`pid` を含めない。通しのテストで、陣営1に届いた全メッセージを調べ、陣営0の方針が含まれていないことを確かめる。

## 5. client

### 5.1 画面

| 画面 | 中身 |
|---|---|
| タイトル | 「ステージ」「対戦」。対戦は第1章を終えるまで選べない |
| ステージ選択 | 章と面、取った星 |
| 配置 | 戦場、手持ち（対戦は編成と予算）、ひな形、方針の切り替え、「開戦」 |
| 戦闘 | 戦場、残り時間、号令、早送り（1人用だけ） |
| 結果 | 勝敗、星、振り返り、「もう一度」「次へ」「戻る」 |
| 部屋 | 「部屋を作る」「コードで入る」、名前、相手待ち、通算成績 |

- Phaser のシーンとして作る。名前とコードの入力だけ、素の HTML の入力欄を重ねる。
- 配置の操作：手持ちの部隊を選んでマスを押すと置く。置いた部隊を引きずると動く。ほかの部隊の上に落とすと入れ替わる。置いた部隊を押すと、方針の切り替えと「外す」が出る。マウスとタッチの両方で同じに動く。
- 号令の操作：相手（全軍・左翼・中央・右翼）を押す → 号令（突撃・堅守・後退）を押す。残りの回数は3つの印で示す。相手を選んだとき、対象の部隊を光らせる。

### 5.2 戦闘を映す仕組み

```ts
interface BattleSource {
  onFrame(cb: (frame: { tick: number; view: BattleView; events: BattleEvent[] }) => void): void;
  onEnd(cb: (summary: BattleSummary) => void): void;      // 決着したときの振り返り
  order(target: OrderTarget, kind: OrderKind): void;
  canOrder(target: OrderTarget, kind: OrderKind): boolean;  // まだ渡していない号令のぶんも数に入れる
  setSpeed?(mult: number): void;       // 1人用だけ。ないときは、早送りのボタンを出さない
  dispose(): void;
}
```

- 戦闘の画面は、`BattleSource`・戦場・見る側の陣営（`viewer`）を、開始時に受け取る。自軍かどうか、残りの号令、色、号令の相手は、すべて `viewer` で決める。`viewer` が 1 なら、上下左右を返して自軍を下に映す。
- 翼の呼び方は、いつも見ている人から見た左右にする。engine は、その陣営から見た左右で翼を持つので、敵軍の翼は左右を入れ替えて表示する。

- `LocalBattleSource`：ブラウザで engine を動かす。実時間をためて 0.1 秒ごとに `step` を呼ぶ（早送りは2倍ためる）。場面は2刻みごとに出す（対戦と同じ見え方にする）。
- `RemoteBattleSource`：サーバーの `snap` をそのまま流す。
- どちらも、出来事は「前の場面のあとに起きた分」をまとめて渡す。決着した刻みは、2刻みを待たずにすぐ出す。
- 戦闘の画面は `BattleSource` だけを見る。前の場面と今の場面のあいだを、時間で補って描く。
- 部隊の描き方は「戦場の座標 → 画面の座標」の変換を1か所（`FieldView`）に閉じ込める。段階5の斜め視点は、この変換と絵の組を差し替えて足す。

### 5.3 見た目

- ドット絵。1マス 24px。部隊は、兵数に応じた数の小さな兵（4×4px、最大16人）と、兵種を示す旗で描く。兵が減ると、描く兵も減る。
- 陣営の色は2色（自軍と敵軍）。対戦でも、自分がいつも同じ色で下にいる。
- 士気は、旗の高さで示す（下がるほど旗が下がる）。数字や棒は常には出さない。部隊を押している間だけ、兵数と士気を出す。
- 画面の内部の大きさは、縦長（スマホ）が 320 × 568 以上、横長（PC）が 640 × 400。戦場（288 × 384）は同じ大きさで描き、操作の欄を、縦長では下に、横長では右に置く。拡大は Phaser の FIT に任せる。
- 文字は DotGothic16 の 16px と 32px だけ。平らな塗り、2px 単位の枠。グラデーション・ぼかした影・光彩・角丸は使わない。
- 絵は、ドットの並びを書いたデータから、起動時にテクスチャを作る（画像ファイルを置かない）。段階1は、色のついた四角と点の仮の絵でよい。
- 音は効果音だけ。WebAudio で合成する（太鼓、ぶつかる音、敗走、勝ち負け）。音のファイルは置かない。最初の操作で音を解禁する。

### 5.4 保存

`localStorage` に、1つのキー（`jinkei-gassen/v1`）で JSON を置く：面ごとの最高の星、名前、`pid`、保存した陣形（段階5）。読み書きは try/catch で包み、使えなくても遊べるようにする。

保存した陣形（名前、配置エリアの中の座標で書いた配置と方針、兵種ごとの数）の細部と、手持ちや予算に合わないときの扱いは、段階5に入る前に書き足す。

### 5.5 動かして確かめるための口

開発時だけ、`window.__jg` に、いまの画面・戦闘の状態・面を飛ばす操作を出す。ブラウザを自動で操作して確かめるときに使う。本番のビルドには含めない。
